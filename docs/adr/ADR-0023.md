# ADR-0023 — Authorization: capabilities, checked up the tree

- **Status:** proposed (amends ADR-0020)
- **Date:** 2026-11-18
- **Scope:** `lib/go/authz`, `lib/go/backend/identityx`, `sdk/go/IdentityX`, `sdk/ts/identityx-{access,react}`, `lib/ts/front-core`, `api/{identityx,informd,payssage,univents}` (incl. `cloudflare/`)

## Why

Access control was rewritten several times (manual checks, roles,
Zanzibar, back to roles). Today it is about 140 hand-written checks that
ask "is this person staff?", copy the "else the parent's role" logic in
every backend, and load the same rows twice. IdentityX's capabilities
exist but nothing uses them (production: 0 capabilities, 0 assignments).

## The idea

Code never asks *who you are*. It asks **can you do this action here?**

```go
err := access.Can(ctx, "markAttendance", authz.Ref{Kind: "edition", ID: editionID})
```

The operation names only the action. Who may do it, and at which level,
is in the capabilities.

## Capabilities

### Names

A capability is **an action granted at a level**: `<level>.<action>`, or
`<level>.*` for every action at that level. Levels are singular and match
`Ref.Kind` (`platform`, `org`, `event`, `edition`, `program`, …).

Granted at a level, a capability covers that node **and everything below
it**:

| Capability | Held | Covers |
|---|---|---|
| `program.markAttendance` | on the pivot row of program P | program P |
| `edition.markAttendance` | on the pivot row of edition E | every program in edition E |
| `event.*` | on the pivot row of event V | everything in event V (the event owner) |
| `platform.markAttendance` | in IdentityX, general | every program everywhere (e.g. a moderator) |
| `platform.*` | in IdentityX, general | everything (super admin) |

There is no bare `*`: a wildcard always names its level.

### Two places, one meaning

- **On a pivot row** (in the app): covers that node and below. This is
  every grant on a specific resource. The app's database is its only
  copy.
- **General** (in IdentityX, assigned to users and API keys): covers
  **every node of its level**. `platform.*` is the root case; a company
  where every writer may write every document gives `document.write`.

IdentityX never stores grants on specific nodes. The token carries only
general capabilities.

### The catalog

The app declares each action once, with the levels it can be granted at:

```go
access.Action("markAttendance", "platform", "org", "event", "edition", "program")
```

The catalog it sends to IdentityX holds the derived capabilities
(`platform.markAttendance` … `program.markAttendance`) and each level's
`<level>.*`; nobody writes those by hand. IdentityX uses it to validate
general grants and API key lists, and to list them in its admin screen.

**Each app sends its catalog on startup** in the background, never
blocking it: `PUT /projects/{project_id}/capabilities` with
`If-None-Match: <hash>`. The sync must never wake IdentityX's container
when nothing changed (see *Amends ADR-0020*).

Removing an action from the catalog **does not touch pivot rows**: `Can`
ignores names it doesn't know, so stale names are harmless. Cleaning them
up, if ever wanted, is a deliberate migration.

## Roles are pivot tables

- A role is **being in a pivot table**: a row in `event_members` makes
  you a member of that event. Each app keeps its pivots, as today.
- **The row stores the capabilities that person has there**, expanded.
  After the row is created, the row is the truth.
- **Roles are named bundles, defined in the app's code** next to its
  catalog:

  ```go
  access.Role("staff", "event.markAttendance", "event.checkIn")
  access.Role("owner", "event.*")
  ```

  Creating a row applies a bundle: it writes the role's name to the
  existing `role` column and the bundle's names to `capabilities`.
- **`role` is a label, never a check.** It means "started as staff".
  Changing a bundle in code changes no existing row; the UI can show
  "Staff (custom)" when a row's capabilities no longer match its bundle.
- **New capabilities are opt-in**: they reach no row until someone grants
  them. Giving one to everyone is a deliberate migration.
- **The owner is the row with `<level>.*`**: `event.*` on their event,
  which covers everything in it, new actions included. `owner_id` columns
  stop deciding access.

## Granting

Writing capabilities onto a row is itself an action the app declares
(by convention `<level>.manageMembers`) and checks with `Can`. Which
bundles or names a granter may hand out is app policy: hard-code it, or
write the limits in the service.

One rule is not optional, and the lib provides it:

```go
err := access.CanGrant(ctx, authz.Ref{Kind: "event", ID: eventID}, caps)
```

**The ceiling:** a granter can only grant names they hold at that node
or above. Without it, anyone with `event.manageMembers` could write
`event.*` onto their own row.

Apps also refuse to remove the last `<level>.*` holder of a node, so no
resource is left without an owner.

## The levels

Every app has the same shape: a **platform** level at the top, then its
own levels, each with an optional pivot.

| App | Levels (top → bottom) |
|---|---|
| IdentityX | platform → org → project |
| Payssage | platform → org → wallet |
| Informd | platform → namespace → form |
| Univents | platform → org → event → edition |

The **platform** level is always the token: no database.

## The token

`subject.capabilities` lists the actor's **general** capabilities, as
plain strings:

```json
{
  "subject": {
    "id": "01a0…", "project_id": "01a0…", "type": "human", "email": "ana@…",
    "capabilities": ["platform.markAttendance", "document.write"]
  }
}
```

- An actor belongs to one project, so its token carries only that
  project's (that app's) capabilities.
- General capabilities are **trusted** from the token. A revoked one stays
  usable **until the token expires: at most 1 hour in production**
  (`ACCESS_TOKEN_LIFETIME`). Revoking something on a pivot row takes
  effect on the next request, because `Can` reads the row.
- Every refresh rebuilds `capabilities` from IdentityX.

### Credentials are bound to their project

Each backend is configured with its `ProjectID`. The middleware in
`lib/go/backend/identityx` rejects any identity whose
`subject.project_id` is a different project, **on both paths**: the JWT
(the claim is already in the token) and the API key (introspection
returns the key's project). Without this, any IdentityX tenant could give
itself `platform.*` in its own project and present it to another app.

## API keys

**A key is its actor, narrowed.** It carries the actor's identity and a
list of capabilities the actor chose for it. The most a key can do is
everything its actor can do:

- **Effective access = what the actor can do ∩ the key's list.** `Can`
  decides for the actor as usual, then requires the key's list to allow
  the action: some entry `<level>.<action>` or `<level>.*` whose level is
  on the chain, platform included.
- The list is a filter only: it never grants. A key listing more than its
  actor holds simply can't use the extra, so minting needs no extra
  check, and anything the actor loses, its keys lose.
- An empty list means the full actor.
- **A key's actor must belong to the key's project.** IdentityX refuses
  to mint one otherwise.

Introspection returns the actor (with its general capabilities) and the
key's list separately.

## How `Can` decides

In `lib/go/authz`, the same for every app. `Can(ctx, action, at)`:

1. **Free check, from the token:** a general `platform.<action>` /
   `platform.*`, or a general `<at.Kind>.<action>` / `<at.Kind>.*`.
2. **A ref with no id** (`authz.Platform`, or `Ref{Kind: "document"}` for
   "any document") stops here: only general capabilities apply to it.
3. **The chain:** from `at` up to the platform, through the app's `Parent`
   (e.g. `[edition:E, event:V, org:O]`).
4. **General capabilities of each level** in the chain, from the token.
5. **The climb:** the actor's pivot rows on the whole chain, fetched in
   one `Capabilities` call, checked bottom up.
6. With an API key, its list must also allow the action (see *API keys*).
7. Nothing → `403`.

General capabilities of a level are checked inside the chain, not before
it: `org.markAttendance` must not reach a personal event that sits in no
org, and only the chain knows which levels a node is under.

```go
func (c *Checker) Can(ctx context.Context, action string, at Ref) error {
    id := idx.IdentityFrom(ctx)
    if id.Key == nil && (id.General(names(Platform, action)...) || id.General(names(at, action)...)) {
        return c.allow(ctx, action, at, "token", at) // free: no query
    }
    chain := []Ref{at, Platform}
    if at.ID != uuid.Nil {
        var err error
        if chain, err = c.chain(ctx, at); err != nil { // [at, …, Platform]
            return err
        }
    }
    if !id.Key.Allows(action, chain) { // nil key allows everything
        return c.deny(ctx, action, at, "key")
    }
    for _, ref := range chain {
        if id.General(names(ref, action)...) {
            return c.allow(ctx, action, at, "token", ref)
        }
    }
    if at.ID == uuid.Nil {
        return c.deny(ctx, action, at, "general-only")
    }
    held, err := c.lookup.Capabilities(ctx, id.Subject, chain)
    if err != nil {
        return err
    }
    for _, ref := range chain {
        if hasAny(held[ref], names(ref, action)) {
            return c.allow(ctx, action, at, "pivot", ref)
        }
    }
    return c.deny(ctx, action, at, "nothing")
}

// what counts at a level: "edition.markAttendance" or "edition.*"
func names(ref Ref, action string) []string {
    return []string{ref.Kind + "." + action, ref.Kind + ".*"}
}
```

Without an API key, step 1 returns before any query. With one, the chain
is needed first, because the key's list is matched against it.

## What each app writes

Two batched functions and nothing else:

```go
// Who is above these nodes?
Parent(ctx context.Context, refs []authz.Ref) (map[authz.Ref]authz.Ref, error)
// Which capabilities does this person have at these nodes? (their pivot rows)
Capabilities(ctx context.Context, who uuid.UUID, refs []authz.Ref) (map[authz.Ref][]string, error)
```

Each is a `switch` on the level that groups the refs by kind and runs
**one query per level** (`WHERE user_id = $1 AND <level>_id = ANY($2)`),
calling the repos it already has. A check costs as many queries as the
chain has levels, not as many as there are items or actions.

## What the front asks

The front asks **the app it is already talking to**, so it wakes nothing
extra and never writes to IdentityX. The app writes no code for it:
`lib/go/authz` provides both forms.

- **`POST /me/can`**, mounted by the lib on every app:

  ```
  POST /me/can
  { "checks": [{ "ref": "edition:7f3a…", "actions": ["markAttendance", "checkIn"] }] }
  → { "edition:7f3a…": ["markAttendance"] }
  ```

  The front asks only for what the screen shows, never "everything I can
  do". All checks in one request share the batched lookups, so a list
  page of 50 editions costs one query per level.
- **`can` in responses:** `access.Allowed(ctx, refs, actions...)` returns
  the same map for a handler to embed (`"can": ["markAttendance"]`) in the
  reads the front already makes, at zero extra requests.

The backend still enforces every operation; a stale answer only shows or
hides a button.

## Consumers

**TS (`sdk/ts/identityx-access`, hooks in `identityx-react` and the Solid
equivalent):**

```ts
type Ref = `${string}:${string}`            // "edition:7f3a…"
type CanAnswer = Record<Ref, string[]>      // ref → allowed actions

can(baseURL: string, checks: { ref: Ref; actions: string[] }[]): Promise<CanAnswer>
useCan(ref: Ref, ...actions: string[]): { allowed: (action: string) => boolean; loading: boolean }
```

- Fronts never evaluate capabilities themselves: no climb, no `General`,
  no reading the token's list to gate screens. They ask `can`, or read the
  `can` map a response already carries.
- Hooks in one render batch their checks into a single `/me/can`
  request, and the answer is cached for the screen. A write the front
  makes invalidates it.
- Role checks in the fronts (`isOwner`, `data.role === …owner` in the
  member cards) become `allowed("manageMembers")`. `role` is shown, never
  compared.
- Member forms list the app's bundles from `GET /access/roles`, mounted
  by the lib next to `/me/can`. It is static per deploy, so it is a public
  GET cached at the edge under ADR-0020.

**Denials** use one problem (ADR-0022): `forbidden`, carrying `action`
and `ref`, so a front can say "ask an owner for markAttendance". Whether
a caller who can't see a resource gets `403` or `404` stays the
operation's choice, as today.

**Mistakes fail at startup, not in production:**

- `authz.New` panics if a role bundle names a capability the catalog
  doesn't derive.
- `Can` with an action that isn't in the catalog returns an error (a
  `500` and a log line), never a quiet `403`.

**Tests:** `lib/go/authz/authztest` gives a map-backed `Lookup` and a
context with a fake identity (general capabilities, optional key list),
so a handler test states "this person holds `event.*` on V" in one line.

**The token's format:** API key lists and introspection carry
`resource:action` strings today; they become `<level>.<action>`. The
shape stays a list of strings, so `ModernIntrospect`'s `string[]` stands;
`front-core` narrows its `capabilities` type to `string[]`. Production
holds 0 capabilities and 0 assignments, so the format changes in one
release with no compatibility layer: the Go and TS SDKs accept only the
new form.

IdentityX owns authentication, general capabilities, the model and the
SDKs. The apps own grants on their own resources (see *Not doing*).

## Observability

- **Every decision logs one structured line** from the `Checker`:
  subject, key id, action, ref, outcome, and what decided it (`token` and
  the level, `pivot` and the ref, `key`, or `nothing`). Denials at info,
  allows at debug.
- **Every capability write logs one line**: granter, actor, ref, names
  before and after. Apps call the lib's helper when they write a row.

No new infrastructure: these go to the existing logs.

## Rules

- No subject holds a capability outside its own project (credential
  binding).
- A granter only grants names they hold at that node or above (ceiling).
- Every node with a pivot keeps at least one `<level>.*` holder.
- A key never exceeds its actor; its actor is in its project.
- `role` never decides access; `capabilities` does.
- A capability name always names its level; no bare `*`.

## IdentityX API

Everything is per project (one project = one app). The existing
`/projects/{project_id}/capabilities` resource becomes the catalog.

| Method and path | What | Called by |
|---|---|---|
| `GET /projects/{project_id}/capabilities` | the catalog | apps, IdentityX's admin screen |
| `PUT /projects/{project_id}/capabilities` | replace the catalog; `If-None-Match: <hash>` → `304` at the edge | the app, on startup |
| `GET /projects/{project_id}/actors/{actor_id}/capabilities` | an actor's general capabilities | admin screens |
| `PUT /projects/{project_id}/actors/{actor_id}/capabilities` | replace an actor's general capabilities | IdentityX's admin screen |
| `PUT /projects/{project_id}/api-keys/{key_id}/capabilities` | replace an API key's list | whoever manages the key |

Writes check `Can(..., Ref{Kind: "project", ID: project_id})` in
IdentityX: a project admin, or the app's service key, whose actor holds
`project.writeCapabilities` on that project's member row. Every path
verifies that `actor_id` and `key_id` belong to `{project_id}`. The old
`POST` that created one capability goes away; the catalog is only ever
replaced whole.

## Data types

Three pieces of code meet in every check: the IdentityX SDK, `lib/authz`
and the app. They share **one** set of types, defined in the SDK, so no
layer converts between its own versions.

**Strings on the wire** (JSON, token, database):

| Thing | Form | Example |
|---|---|---|
| level | singular, lower case | `edition` |
| action | lowerCamel | `markAttendance` |
| capability | `<level>.<action>` or `<level>.*` | `edition.markAttendance` |
| node | `<level>:<uuid>` | `edition:7f3a…` |

**`sdk/go/IdentityX` (package `idx`): the wire and the token**

```go
type Ref struct {
    Kind string    // a level
    ID   uuid.UUID // zero = "any node of this level"
}                  // JSON: "edition:7f3a…"

type Capabilities []string // subject.capabilities: general only

func (c Capabilities) General(names ...string) bool

type Key struct { // nil unless the caller is an API key with a list
    ID           uuid.UUID
    Capabilities []string
}

func (k *Key) Allows(action string, chain []Ref) bool

type Action struct { // a catalog entry
    Name   string   `json:"action"` // "markAttendance"
    Levels []string `json:"levels"` // ["platform", "event", "edition", "program"]
}

func IdentityFrom(ctx context.Context) *Identity // subject, general capabilities, key
// client.Capabilities.PutCatalog
```

**`lib/go/authz`: the check**

```go
type Ref = idx.Ref // the same type, aliased: apps never convert
var Platform = Ref{Kind: "platform"}

type Lookup interface {
    Parent(ctx context.Context, refs []Ref) (map[Ref]Ref, error)
    Capabilities(ctx context.Context, who uuid.UUID, refs []Ref) (map[Ref][]string, error)
}

type Role struct {
    Name         string
    Capabilities []string
}

type Checker struct{ /* lookup, actions, roles */ }
func New(l Lookup, actions []idx.Action, roles ...Role) *Checker
func (c *Checker) Can(ctx context.Context, action string, at Ref) error
func (c *Checker) Allowed(ctx context.Context, refs []Ref, actions ...string) (map[Ref][]string, error)
func (c *Checker) CanGrant(ctx context.Context, at Ref, caps []string) error
func (c *Checker) Bundle(role string) []string
func (c *Checker) Catalog() []idx.Action // what the startup sync sends
func (c *Checker) Handler() http.Handler // POST /me/can, GET /access/roles
var ErrForbidden = ErrInsufficientRole   // still 403 through the shared mapper
```

`lib/authz` knows no app's levels or tables: only strings, `Ref` and the
`Lookup` it is given.

**The app: its levels, actions, roles and pivots**

```go
// univents/internal/access
const (Platform = "platform"; Org = "org"; Event = "event"; Edition = "edition"; Program = "program")
const MarkAttendance = "markAttendance"

var Checker = authz.New(lookup{…},
    []idx.Action{{Name: MarkAttendance, Levels: []string{Platform, Org, Event, Edition, Program}}},
    authz.Role{Name: "owner", Capabilities: []string{"event.*"}},
    authz.Role{Name: "staff", Capabilities: []string{"event.markAttendance"}},
)

// models: the pivot row
type EventMember struct {
    EventID, UserID uuid.UUID
    Role            string   // label only: "staff"
    Capabilities    []string // text[]: "event.*", "event.markAttendance"
}
```

The app's `Capabilities` returns the rows' lists as they are.

## Not authorization

Business rules stay in the services: ticket access levels, staff-only
programs, "needs a confirmed ticket". Reading someone else's membership
for such a rule (e.g. "is this attendee staff?") uses the same
`Capabilities` function, not `Can`.

Records that belong to their holder (`purchaser_id`, `user_id`) are
checked in the operation.

## Not in the spec

The spec keeps authentication (`security`, `x-scope`) only. Permissions
live in the code, one `Can` line per operation, so nothing can fall out
of sync. `POST /me/can` and `GET /access/roles` are the shared operations
every app's spec includes.

## Amends ADR-0020

ADR-0020 sends every write to the container. The catalog `PUT` is the
one exception, because apps wake often and must not wake IdentityX with
them:

- IdentityX's gateway Worker keeps each project's catalog hash in KV.
- A `PUT /projects/{project_id}/capabilities` whose `If-None-Match`
  equals the stored hash is answered `304` by the Worker, without
  starting the container.
- On a mismatch the Worker forwards the `PUT`; the container replaces the
  catalog and the Worker stores the new hash after a `2xx`.
- If KV can't be read, the Worker forwards (correct, just not free).

## Production today

About 30 membership rows in total across products; Univents has at most
2 events per person. The deepest chain from a URL to a pivot is 3 hops.
Access tokens live 1 hour.

## Migration

One app at a time. Within an app, `Can` replaces the role checks
operation by operation; nothing switches everywhere at once.

- **Per app:** add `capabilities text[]` to each pivot and fill it from
  `role` with the app's role bundles (owner → `<level>.*`, admin and
  staff → today's checks as lists of `<level>.<action>`). `role` stays,
  as a label.
- **Order:** Informd (one form; add its missing owner row), Payssage (add
  owner rows for personal wallets and collectors), IdentityX, Univents
  (its org and edition pivots come with the planned rework).
- **IdentityX:** `platform_roles` becomes general `platform.*`
  capabilities; org and project members get `capabilities` like any
  pivot. Plus the catalog `PUT` and its edge hash, general capabilities in
  the token, key lists, and refusing keys whose actor is outside the
  project.
- **`lib/go/backend/identityx`:** the project binding on both the JWT and
  the API key paths, before any app trusts general capabilities.

## Not doing

- Grants on specific nodes stored in IdentityX (a ledger, or hints in
  the token). The fronts ask the app instead. Revisit only if `/me/can`
  turns out to cost more than the round trip it saves.
- Roles defined or edited in IdentityX (custom roles per tenant).
- A central grant store as the source of truth (Zanzibar, SpiceDB).
- Deny rules: access is only ever granted.
- Resources with two parents.
