# ADR-0023 — Authorization: scopes in the token, roles on the tree

- **Status:** proposed
- **Date:** 2026-11-17
- **Scope:** `lib/go/authz`, `sdk/go/IdentityX`, `api/{identityx,informd,payssage,univents}`

## Why

Access control was rewritten several times (manual checks, roles,
Zanzibar, back to roles) and today it is about 140 hand-written checks:
each backend copies the same "role here, else the parent's role" logic,
loads the resource twice, and IdentityX's capabilities exist but nothing
uses them (production: 0 capabilities, 0 assignments).

Every backend already has the same shape: a tree of resources, and a
role granted on a node applies to that node and everything under it.

## Decision

Two layers, checked together, the way GitHub, Google Cloud and Clerk do it.

**1. Scopes, in the token (IdentityX).**
IdentityX defines capabilities (`domain.action`). A capability is either:
- **served:** assigned to users and API keys in IdentityX and sent in the
  token (e.g. `events.create`, `payssage.admin`). Fronts and backends read
  it from the token.
- **not served:** only a name for an app's permission; never in the token.

IdentityX only provides capabilities; it never decides what they mean.

**2. Roles, on the app's tree.**
Each app keeps its membership table: who, which node, which role. A role
on a node applies to everything below it. A role is a fixed set of
permissions, listed in the app's code. No per-person permission lists.

| App | Tree | Roles |
|---|---|---|
| IdentityX | platform → org → project | owner, admin, member (platform: super_admin, admin, support) |
| Payssage | org or person → wallet → sellers, intents, webhooks | owner, admin, member |
| Informd | namespace → form → steps, fields, responses | owner, admin, member |
| Univents | event → edition → programs, products, badges, … | owner, admin, staff |

**The check.** Code asks one question: may the caller do `X` on this node?
`lib/authz` answers yes if the token has a served capability that covers
`X`, or if the caller's role on the node (or the nearest parent with a
role) includes `X`. The tree walk and the role lookup are written once,
in one query per check.

**Owner.** The owner is a membership row with role `owner`, nothing else.
`owner_id` columns stop deciding access.

**Your own records.** A record that names its holder (`purchaser_id`,
`user_id`) is readable by that holder. This is the one rule outside roles.

**Not authorization.** Business rules stay in the services: ticket access
levels, staff-only programs, "needs a confirmed ticket".

**Platform admins.** IdentityX's platform roles only act on IdentityX.
Another product gets super admins by declaring a served capability for
itself (e.g. `payssage.admin`) and checking it.

## Migration

Production is small (about 30 membership rows in total), so each backend
moves in one step:

- **Univents:** no data change; checks move to `lib/authz`.
- **Payssage:** add an `owner` row for personal wallets and collectors, so
  `OwnerID != caller` checks go away.
- **Informd:** add the missing `owner` row for its one form whose owner
  exists only in `owner_id`.
- **IdentityX:** no data change; the project → org fallback becomes the
  shared tree walk; capabilities gain the served/not-served flag.

## Not doing

- Per-person permission lists inside a role.
- A central grant store (Zanzibar, SpiceDB) or grants for specific
  resources in the token.
- Resources with two parents.

## Open

- Should roles and their permissions also be listed in IdentityX's
  catalog, or stay in each app's code? (Proposed: code, for now.)
- Does a served capability like `univents.admin` cover every event's
  permissions? (Proposed: yes, when it says so explicitly.)
