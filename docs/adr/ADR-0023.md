# ADR-0023 — Authorization: capabilities, checked up the tree

- **Status:** proposed (amends ADR-0004, ADR-0005, ADR-0015, ADR-0016 and ADR-0020)
- **Date:** 2026-11-18
- **Scope:** `lib/go/authz`, `lib/go/backend/identityx`, `tools/go/problemgen`, `sdk/go/IdentityX`, `sdk/ts/identityx-{access,react}`, `lib/ts/front-core`, `api/{identityx,informd,payssage,univents}` (incl. `cloudflare/`)

## Why

Access control was rewritten several times (manual checks, roles,
Zanzibar, back to roles). Today it is about 140 hand-written checks that
ask "is this person staff?", copy the "else the parent's role" logic in
every backend, and load the same rows twice. IdentityX's capabilities
exist but nothing uses them (production: 0 capabilities, 0 assignments).

## The idea

Code never asks *who you are*. It asks **can you do this action here?**

```go
err := access.Can(ctx, "markAttendance", authz.Ref{Kind: "edition", ID: editionID})
```

The operation names only the action. Who may do it, and at which level,
is in the capabilities.

## Capabilities

### Names

A capability is **an action granted at a level**: `<level>.<action>`, or
`<level>.*` for every action at that level. Levels are singular and match
`Ref.Kind` (`platform`, `org`, `event`, `edition`, `program`, …).

Granted at a level, a capability covers that node **and everything below
it**:

| Capability | Held | Covers |
|---|---|---|
| `program.markAttendance` | on the pivot row of program P | program P |
| `edition.markAttendance` | on the pivot row of edition E | every program in edition E |
| `event.*` | on the pivot row of event V | everything in event V (the event owner) |
| `platform.markAttendance` | in IdentityX, general | every program everywhere (e.g. a moderator) |
| `platform.*` | in IdentityX, general | everything (super admin) |

There is no bare `*`: a wildcard always names its level.

### Two places, one meaning

- **On a pivot row** (in the app): covers that node and below. This is
  every grant on a specific resource. The app's database is its only
  copy.
- **General** (in IdentityX, assigned to users and API keys): covers
  **every node of its level**. `platform.*` is the root case; a company
  where every writer may write every document gives `document.write`.

IdentityX never stores grants on specific nodes. The token carries only
general capabilities.

### Two namespaces

Every project's capabilities are its own. **IdentityX's capabilities**
(levels `platform → org → project`, e.g. `project.writeCapabilities`) are
about managing IdentityX: orgs, projects, their catalogs, keys and
members. **A project's capabilities** (e.g. Univents'
`platform.markAttendance`) are the app's, from that project's catalog. A
`platform.*` in IdentityX's namespace is TrieOH staff in IdentityX; it
means nothing in any app.

General grants are stored per project: (actor, project, name).

### The catalog

The app declares each action once, with the levels it can be granted at:

```go
access.Action("markAttendance", "platform", "org", "event", "edition", "program")
```

The catalog it sends to IdentityX holds the derived capabilities
(`platform.markAttendance` … `program.markAttendance`) and each level's
`<level>.*`; nobody writes those by hand. IdentityX uses it to validate
general grants and API key lists, and to list them in its admin screen.

**Each app sends its catalog on startup** in the background, never
blocking it: `PUT /projects/{project_id}/capabilities` with
`If-None-Match: <hash>`. The sync must never wake IdentityX's container
when nothing changed (see *Amends ADR-0020*).

Removing an action from the catalog **does not touch pivot rows**: `Can`
ignores names it doesn't know, so stale names are harmless. Cleaning them
up, if ever wanted, is a deliberate migration. **A removed name is
retired, never reused:** IdentityX keeps retired names per project and
rejects a catalog that brings one back, so old grants on rows can't come
back to life under a new meaning.

## Roles are pivot tables

- A role is **being in a pivot table**: a row in `event_members` makes
  you a member of that event. Each app keeps its pivots, as today.
- **The row stores the capabilities that person has there**, expanded.
  After the row is created, the row is the truth.
- **Roles are named bundles, defined in the app's code** next to its
  catalog:

  ```go
  access.Role("staff", "event.markAttendance", "event.checkIn")
  access.Role("owner", "event.*")
  ```

  Creating a row applies a bundle: it writes the role's name to the
  existing `role` column and the bundle's names to `capabilities`.
- **`role` is a label, never a check.** It means "started as staff".
  Changing a bundle in code changes no existing row; the UI can show
  "Staff (custom)" when a row's capabilities no longer match its bundle.
- **New capabilities are opt-in**: they reach no row until someone grants
  them. Giving one to everyone is a deliberate migration.
- **The owner is the row with `<level>.*`**: `event.*` on their event,
  which covers everything in it, new actions included. `owner_id` columns
  stop deciding access.

## Granting

Writing capabilities onto a row is itself an action the app declares
(by convention `<level>.manageMembers`) and checks with `Can`. Which
bundles or names a granter may hand out is app policy: hard-code it, or
write the limits in the service.

One rule is not optional, and the lib enforces it (see *The lib owns the
write* below):

**The ceiling** (for pivot rows, inside an app's namespace): a granter
can only grant names they hold at that node or above. Without it, anyone with `event.manageMembers` could write
`event.*` onto their own row. Exactly:

- Granting `<level>.<action>` at node N needs `Can(action, N)` to pass
  for the granter.
- Granting `<level>.*` at N needs the granter to hold `<l>.*` at N or at
  a node above it (a general `<l>.*` or `platform.*` counts). Holding
  `event.*` on V lets you grant `edition.*` on an edition of V; holding
  `event.markAttendance` does not.
- **Revoking needs the same as granting:** you can only remove what you
  could have given. A write replaces a row's list, so the ceiling is
  checked on the **diff**: every name added and every name removed.
- The ceiling uses the granter's **effective** access: with an API key,
  the key's list applies too, so a narrowed key can't grant beyond
  itself.

Apps also refuse to remove the last `<level>.*` holder of a node, so no
resource is left without an owner.

**The lib owns the write.** Apps never write capabilities onto a row
directly; they call

```go
err := access.Grant(ctx, authz.Ref{Kind: "event", ID: eventID}, who, "staff", caps)
err := access.Remove(ctx, authz.Ref{Kind: "event", ID: eventID}, who)
err := access.Create(ctx, parent, authz.Ref{Kind: "event", ID: eventID}, "owner")
```

- **`Grant`** checks the action (`<level>.manageMembers`), loads the
  row's current list, runs the ceiling on the diff, refuses to remove the
  last `<level>.*` holder, writes the row (label and names) through the
  app's `PutRow`, and logs the change.
- **`Remove`** deletes a member's row with the same checks: the ceiling
  on everything the row held, and the last-owner rule.
- **`Create`** is for a new node: it checks `Can("create<Kind>", parent)`,
  then writes the caller's own row on the new node from the given bundle
  (normally the owner's `<level>.*`), in the same transaction as the
  node. That is how the first owner exists without anyone holding
  `manageMembers` on a node that didn't exist.

Every grant rule lives in these three functions.

**Changing a bundle for existing rows** is a deliberate migration, and
the lib provides it: `access.Extend("staff", "event.refund")` adds names
to every row labelled `staff` (and logs each row). New actions stay
opt-in; this is how "every staff gets refunds" is done in one line.

**General grants are not ceilinged.** They are written in IdentityX by
whoever holds IdentityX's `project.writeCapabilities` on that project
(its project admins, by IdentityX's own pivots). Those people can give
any name from the project's catalog, `platform.*` included, to any actor
or key of that project. That is the bootstrap: a project admin picks
which account is the app's super user, whatever email they use there.

## The levels

Every app has the same shape: a **platform** level at the top, then its
own levels, each with an optional pivot.

| App | Levels (top → bottom) |
|---|---|
| IdentityX | platform → org → project |
| Payssage | platform → org → wallet |
| Informd | platform → namespace → form |
| Univents | platform → org → event → edition |

The **platform** level is always the token: no database.

## The token

`subject.capabilities` lists the actor's **general** capabilities, as
plain strings:

```json
{
  "subject": {
    "id": "01a0…", "project_id": "01a0…", "type": "human", "email": "ana@…",
    "capabilities": ["platform.markAttendance", "document.write"]
  }
}
```

- A token carries **only the general capabilities of its own project**
  (`subject.project_id`). A platform account (`project_id` NULL) logs in
  to IdentityX itself, so its token carries IdentityX's namespace only.
- General capabilities are **trusted** from the token. A revoked one stays
  usable **until the token expires: at most 1 hour in production**
  (`ACCESS_TOKEN_LIFETIME`). Revoking something on a pivot row takes
  effect on the next request, because `Can` reads the row.
- Every refresh rebuilds `capabilities` from IdentityX.

### Credentials are bound to their project

Each backend is configured with its `ProjectID`. The middleware in
`lib/go/backend/identityx` binds every credential to it:

- **JWT:** `subject.project_id` must equal the backend's project. A token
  with a NULL `project_id` (a platform account) is accepted only by
  IdentityX itself. (Per-project signing keys already make a foreign JWT
  fail; this check states it.)
- **API key:** the **key's** `project_id` must equal the backend's
  project. The actor's `project_id` is not used: for a platform account
  it is NULL.

Without this, any IdentityX tenant could give itself `platform.*` in its
own project and present it to another app, and TrieOH staff's
IdentityX-level `platform.*` would reach every app.

**IdentityX itself** accepts credentials from every project (it serves
them all), so it binds by namespace instead:

- It trusts **general capabilities only from platform accounts**
  (`project_id` NULL). Those are IdentityX's namespace.
- For any project-bound credential (a token of project P, or a key with
  `project_id = P`), IdentityX **ignores its general capabilities**: they
  are P's namespace, and a P admin may have given someone `platform.*`
  there. It decides only from the actor's IdentityX member rows (org and
  project members).
- A project-bound key is accepted by IdentityX only if it is
  `unrestricted`. Its list names P's capabilities, which mean nothing in
  IdentityX. The app's service key is unrestricted.

## API keys

**A key is its actor, narrowed.** It carries the actor's identity and a
list of capabilities the actor chose for it. The most a key can do is
everything its actor can do:

- **Effective access = what the actor can do ∩ the key's list.** `Can`
  decides for the actor as usual, then requires the key's list to allow
  the action: some entry `<level>.<action>` or `<level>.*` whose level is
  on the chain, platform included.
- The list is a filter only: it never grants. A key listing more than its
  actor holds simply can't use the extra, and anything the actor loses,
  its keys lose.
- **Unrestricted is a flag, never an empty list.** `api_keys.unrestricted`
  means "the full actor". With the flag off, an empty list allows
  nothing. A list that empties by accident (a renamed action) narrows the
  key; it never widens it.
- **The list stores names as text**, like pivot rows, not foreign keys to
  the catalog. Replacing the catalog never deletes a key's entries;
  unknown names allow nothing.

**Every key belongs to a project:** `api_keys.project_id`, set at mint.
A key's actor either is an actor of that project (`actors.project_id`),
or is a platform account (`actors.project_id` NULL) that is a member of
it, like an app's service key. Introspection returns the key's
`project_id`, the actor, **only the actor's general capabilities in that
project**, and the key's list.

**Creating a key** needs either a non-empty list or `unrestricted: true`.
A request with neither is rejected (`400`), so no key is ever silently
dead or silently all-powerful.

**Who mints:** you can always mint keys for yourself, **from a session or
an unrestricted key**. A narrowed key can't mint keys or edit any key's
list, so a leaked narrowed key can't mint itself an unrestricted sibling.
Holders of
IdentityX's `project.manageKeys` on a project (its project admins) can
also mint keys for that project's **`service` and `machine` actors** (an actor of the project, or a platform account that
is a member of it, like the app's service key); the key gets that
project's `project_id`. Never for a `human`, and never for an actor of
another project. IdentityX can't see apps' pivot rows, so a key minted
for a person would let its minter act as that person in the app; humans
mint their own keys. Minting for a service actor needs no ceiling: a
holder of `project.manageKeys` can already grant that actor anything in
the project.

## How `Can` decides

In `lib/go/authz`, the same for every app. `Can(ctx, action, at)`:

1. **Free check, from the token:** a general `platform.<action>` /
   `platform.*`, or a general `<at.Kind>.<action>` / `<at.Kind>.*`.
2. **A ref with no id** (`authz.Platform`, or `Ref{Kind: "document"}` for
   "any document") stops here: only general capabilities apply to it.
3. **The chain:** from `at` up to the platform, through the app's `Parent`
   (e.g. `[edition:E, event:V, org:O]`).
4. **General capabilities of each level** in the chain, from the token.
5. **The climb:** the actor's pivot rows on the whole chain, fetched in
   one `Capabilities` call, checked bottom up.
6. With an API key, its list must also allow the action (see *API keys*).
7. Nothing → `403`.

General capabilities of a level are checked inside the chain, not before
it: `org.markAttendance` must not reach a personal event that sits in no
org, and only the chain knows which levels a node is under.

```go
func (c *Checker) Can(ctx context.Context, action string, at Ref) error {
    id := idx.IdentityFrom(ctx)
    if id.Key == nil && (id.General(names(Platform, action)...) || id.General(names(at, action)...)) {
        return c.allow(ctx, action, at, "token", at) // free: no query
    }
    chain := []Ref{at, Platform}
    if at.ID != uuid.Nil {
        var err error
        if chain, err = c.chain(ctx, at); err != nil { // [at, …, Platform]
            return err
        }
    }
    if !id.Key.Allows(action, chain) { // nil or unrestricted key allows everything
        return c.deny(ctx, action, at, "key")
    }
    for _, ref := range chain {
        if id.General(names(ref, action)...) {
            return c.allow(ctx, action, at, "token", ref)
        }
    }
    if at.ID == uuid.Nil {
        return c.deny(ctx, action, at, "general-only")
    }
    held, err := c.lookup.Capabilities(ctx, id.Subject, chain)
    if err != nil {
        return err
    }
    for _, ref := range chain {
        if hasAny(held[ref], names(ref, action)) {
            return c.allow(ctx, action, at, "pivot", ref)
        }
    }
    return c.deny(ctx, action, at, "nothing")
}

// what counts at a level: "edition.markAttendance" or "edition.*"
func names(ref Ref, action string) []string {
    return []string{ref.Kind + "." + action, ref.Kind + ".*"}
}
```

Without an API key, step 1 returns before any query. With one, the chain
is needed first, because the key's list is matched against it.

## What each app writes

Two batched reads, and three small functions for the lib's writes:

```go
// Who is above these nodes?
Parent(ctx context.Context, refs []authz.Ref) (map[authz.Ref]authz.Ref, error)
// Which capabilities does this person have at these nodes? (their pivot rows)
Capabilities(ctx context.Context, who uuid.UUID, refs []authz.Ref) (map[authz.Ref][]string, error)
// Write or delete one person's row at one node (called only by Grant, Remove,
// Create and Extend). nil caps deletes the row.
PutRow(ctx context.Context, who uuid.UUID, ref authz.Ref, role string, caps []string) error
// How many rows at this node hold <level>.*? (the last-owner rule)
Owners(ctx context.Context, ref authz.Ref) (int, error)
// Every row labelled with this role (for Extend)
RowsWithRole(ctx context.Context, role string) ([]authz.Row, error)
```

Each is a `switch` on the level that groups the refs by kind and runs
**one query per level** (`WHERE user_id = $1 AND <level>_id = ANY($2)`),
calling the repos it already has. A check costs as many queries as the
chain has levels, not as many as there are items or actions.

## What the front asks

The front asks **the app it is already talking to**, so it wakes nothing
extra and never writes to IdentityX. The app writes no code for it:
`lib/go/authz` provides both forms.

- **`POST /me/can`**, mounted by the lib on every app:

  ```
  POST /me/can
  { "checks": [{ "ref": "edition:7f3a…", "actions": ["markAttendance", "checkIn"] }],
    "grants": [{ "ref": "event:19c2…", "member": "01b2…", "names": ["event.*"] }] }
  → { "can":    { "edition:7f3a…": ["markAttendance"] },
      "grants": [true] }
  ```

  A `grants` entry asks "may I change this member's row at this ref to
  these names?": the same checks `access.Grant` runs (ceiling on the diff,
  last owner), without writing.

  The front asks only for what the screen shows, never "everything I can
  do". All checks in one request share the batched lookups, so a list
  page of 50 editions costs one query per level.
- **`can` in responses:** `access.Allowed(ctx, refs, actions...)` returns
  the same map for a handler to embed (`"can": ["markAttendance"]`) in the
  reads the front already makes, at zero extra requests.

The backend still enforces every operation; a stale answer only shows or
hides a button.

## Consumers

**TS (`lib/ts/front-core`, hooks for React and Solid):** browsers never
hold a token; they reach the apps through the BFF proxy
(`createBffProxyFetchers`). `can` goes over that same transport, so it
carries the session like every other call. `sdk/ts/identityx-access`
stays server-only.

```ts
type Ref = `${string}:${string}`            // "edition:7f3a…"
type CanAnswer = Record<Ref, string[]>      // ref → allowed actions

can(fetchers: BffFetchers, checks: { ref: Ref; actions: string[] }[]): Promise<CanAnswer>
useCan(ref: Ref, ...actions: string[]): { allowed: (action: string) => boolean; loading: boolean }
```

- Fronts never evaluate capabilities themselves: no climb, no `General`,
  no reading the token's list to gate screens. They ask `can`, or read the
  `can` map a response already carries.
- Hooks in one render batch their checks into a single `/me/can`
  request, and the answer is cached for the screen. A write the front
  makes invalidates it.
- Member cards: `isOwner` is about the **listed** member, so it becomes
  "this row holds `<level>.*`" (the row's own capabilities), and the
  edit/remove buttons on that row come from a `grants` check for it.
  `role` is shown, never compared.
- Member forms list the app's bundles from `GET /access/roles`, mounted
  by the lib next to `/me/can`. It is static per deploy, so it is a public
  GET cached at the edge under ADR-0020. Which bundles the viewer may give
  on this row comes from `grants` checks, not from that list.

**Denials** use one problem (ADR-0022): `forbidden`, carrying `action`
and `ref`, so a front can say "ask an owner for markAttendance". Because
it carries data, it is a typed error (`*authz.ForbiddenError`) defined
once in the shared `api/problems.yml`, mapped by an `errors.As` case in
problemgen's shared prelude, replacing `ErrInsufficientRole` there. Whether
a caller who can't see a resource gets `403` or `404` stays the
operation's choice, as today.

**Mistakes fail at startup, not in production:**

- `authz.New` panics if a role bundle names a capability the catalog
  doesn't derive.
- `Can` with an action that isn't in the catalog returns an error (a
  `500` and a log line), never a quiet `403`. That is for actions written
  in code.
- `/me/can` takes actions from the client, so an unknown one only answers
  "not allowed" for that entry (and logs it); the rest of the batch is
  answered normally.

**Tests:** `lib/go/authz/authztest` gives a map-backed `Lookup` and a
context with a fake identity (general capabilities, optional key list),
so a handler test states "this person holds `event.*` on V" in one line.

**The token's format:** API key lists and introspection carry
`resource:action` strings today; they become `<level>.<action>`. The
shape stays a list of strings, so `ModernIntrospect`'s `string[]` stands;
`front-core` and `sdk/ts/identityx` narrow their `capabilities` types
(today a `Record`) to `string[]`. Key creation sends a list or
`unrestricted: true`; the Payssage front's wallet key sends
`unrestricted: true` from the same release. Production
holds 0 capabilities and 0 assignments, so the format changes in one
release with no compatibility layer: the Go and TS SDKs accept only the
new form.

IdentityX owns authentication, general capabilities, the model and the
SDKs. The apps own grants on their own resources (see *Not doing*).

## Observability

- **Every decision logs one structured line** from the `Checker`:
  subject, key id, action, ref, outcome, and what decided it (`token` and
  the level, `pivot` and the ref, `key`, or `nothing`). Denials at info,
  allows at debug.
- **Every grant write logs one line**: granter, actor, ref, names before
  and after. `access.Grant` writes it for pivot rows; IdentityX writes the
  same line for general grants, key lists, and **key mint and revoke**
  (minter, key id, actor, project, list or `unrestricted`).
- **A log level switch** (`LOG_LEVEL`, default `info`) on every backend,
  so allows at debug can be turned on when chasing a bug. It gates the
  whole logger, the OTLP tee to Grafana included, so debug lines never
  leave the box by accident.

No new infrastructure: these go to the existing logs.

## Rules

- No subject holds a capability outside its own project (credential
  binding on the token's and the key's project; general grants stored per
  project).
- On pivot rows, a granter only grants or revokes names they hold at that
  node or above, with their effective access, checked on the diff
  (enforced once, in the lib's `Grant`, `Remove` and `Create`).
- General grants are written only by holders of IdentityX's
  `project.writeCapabilities` on that project, with any name from its
  catalog.
- Every node with a pivot keeps at least one `<level>.*` holder
  (`access.Grant` and `access.Remove`).
- IdentityX trusts general capabilities only from platform accounts; a
  project-bound credential acts in IdentityX only through its actor's
  IdentityX member rows, and only an unrestricted key is accepted there.
- Only a session or an unrestricted key mints keys or edits key lists.
- A key never exceeds its actor; it belongs to one project, and its actor
  is of that project or a platform member of it.
- A key is minted only for its minter, or by a holder of
  `project.manageKeys` for a `service` or `machine` actor of that project.
- Only the `unrestricted` flag makes a key the full actor; a key with
  neither a list nor the flag is never created.
- `role` never decides access; `capabilities` does.
- A capability name always names its level; no bare `*`.

## IdentityX API

Everything is per project (one project = one app). The existing
`/projects/{project_id}/capabilities` resource becomes the catalog.

| Method and path | What | Called by |
|---|---|---|
| `GET /projects/{project_id}/capabilities` | the catalog | apps, IdentityX's admin screen |
| `PUT /projects/{project_id}/capabilities` | replace the catalog; `If-None-Match: <hash>` → `304` at the edge | the app, on startup |
| `GET /projects/{project_id}/actors/{actor_id}/capabilities` | an actor's general capabilities | admin screens |
| `PUT /projects/{project_id}/actors/{actor_id}/capabilities` | replace an actor's general capabilities | IdentityX's admin screen |
| `POST /projects/{project_id}/api_keys` | mint a key: a list or `unrestricted: true`, else `400` | the actor itself (session or unrestricted key), or a `project.manageKeys` holder for a service/machine actor |
| `PUT /projects/{project_id}/api_keys/{key_id}/capabilities` | replace an API key's list | the key's actor (session or unrestricted key), or a `project.manageKeys` holder |

Catalog and general-grant writes check
`Can("writeCapabilities", Ref{Kind: "project", ID: project_id})` in
IdentityX's namespace: a project admin, or the app's service key, whose
platform actor holds `project.writeCapabilities` on that project's member
row. Actor general grants store names as text (like keys and pivot rows),
not foreign keys to the catalog, so replacing the catalog never deletes a
grant. Every path
verifies that `actor_id` and `key_id` belong to `{project_id}`. The old
`POST` that created one capability goes away; the catalog is only ever
replaced whole.

## Data types

Three pieces of code meet in every check: the IdentityX SDK, `lib/authz`
and the app. They share **one** set of types, defined in the SDK, so no
layer converts between its own versions.

**Strings on the wire** (JSON, token, database):

| Thing | Form | Example |
|---|---|---|
| level | singular, lower case | `edition` |
| action | lowerCamel | `markAttendance` |
| capability | `<level>.<action>` or `<level>.*` | `edition.markAttendance` |
| node | `<level>:<uuid>` | `edition:7f3a…` |

**`sdk/go/IdentityX` (package `idx`): the wire and the token**

```go
type Ref struct {
    Kind string    // a level
    ID   uuid.UUID // zero = "any node of this level"
}                  // JSON: "edition:7f3a…"

type Capabilities []string // subject.capabilities: general only

func (c Capabilities) General(names ...string) bool

type Key struct { // nil unless the caller is an API key
    ID           uuid.UUID
    ProjectID    uuid.UUID
    Unrestricted bool     // the full actor; never implied by an empty list
    Capabilities []string // names as text
}

func (k *Key) Allows(action string, chain []Ref) bool

type Action struct { // a catalog entry
    Name   string   `json:"action"` // "markAttendance"
    Levels []string `json:"levels"` // ["platform", "event", "edition", "program"]
}

func IdentityFrom(ctx context.Context) *Identity // subject, general capabilities, key
// client.Capabilities.PutCatalog
```

**`lib/go/authz`: the check**

```go
type Ref = idx.Ref // the same type, aliased: apps never convert
var Platform = Ref{Kind: "platform"}

type Lookup interface {
    Parent(ctx context.Context, refs []Ref) (map[Ref]Ref, error)
    Capabilities(ctx context.Context, who uuid.UUID, refs []Ref) (map[Ref][]string, error)
    PutRow(ctx context.Context, who uuid.UUID, ref Ref, role string, caps []string) error
    Owners(ctx context.Context, ref Ref) (int, error)
    RowsWithRole(ctx context.Context, role string) ([]Row, error)
}

type Row struct {
    Who          uuid.UUID
    Ref          Ref
    Role         string
    Capabilities []string
}

type Role struct {
    Name         string
    Capabilities []string
}

type Checker struct{ /* lookup, actions, roles */ }
func New(l Lookup, actions []idx.Action, roles ...Role) *Checker
func (c *Checker) Can(ctx context.Context, action string, at Ref) error
func (c *Checker) Allowed(ctx context.Context, refs []Ref, actions ...string) (map[Ref][]string, error)
func (c *Checker) Grant(ctx context.Context, at Ref, who uuid.UUID, role string, caps []string) error // checks, writes, logs
func (c *Checker) MayGrant(ctx context.Context, at Ref, who uuid.UUID, caps []string) error             // the same checks, no write
func (c *Checker) Remove(ctx context.Context, at Ref, who uuid.UUID) error
func (c *Checker) Create(ctx context.Context, parent, node Ref, role string) error
func (c *Checker) Extend(ctx context.Context, role string, names ...string) error
func (c *Checker) Bundle(role string) []string
func (c *Checker) Catalog() []idx.Action // what the startup sync sends
func (c *Checker) Handler() http.Handler // POST /me/can, GET /access/roles
type ForbiddenError struct{ Action string; Ref Ref } // the `forbidden` problem, 403
```

`lib/authz` knows no app's levels or tables: only strings, `Ref` and the
`Lookup` it is given.

**The app: its levels, actions, roles and pivots**

const (Platform = "platform"; Org = "org"; Event = "event"; Edition = "edition"; Program = "program")
const MarkAttendance = "markAttendance"

The app's `Capabilities` returns the rows' lists as they are.

## Not authorization

Business rules stay in the services: ticket access levels, staff-only
programs, "needs a confirmed ticket". Reading someone else's membership
for such a rule (e.g. "is this attendee staff?") uses the same
`Capabilities` function, not `Can`.

Records that belong to their holder (`purchaser_id`, `user_id`) are
checked in the operation.

## Not in the spec

The spec keeps authentication (`security`, `x-scope`) only. Permissions
live in the code, one `Can` line per operation, so nothing can fall out
of sync. `POST /me/can` and `GET /access/roles` are the shared operations
every app's spec includes.

## Amends ADR-0020

ADR-0020 sends every write to the container. The catalog `PUT` is the
one exception, because apps wake often and must not wake IdentityX with
them:

- IdentityX's gateway Worker keeps each project's catalog hash in KV.
- A `PUT /projects/{project_id}/capabilities` whose `If-None-Match`
  equals the stored hash is answered `304` by the Worker, without
  starting the container.
- On a mismatch the Worker forwards the `PUT`; the container replaces the
  catalog and the Worker stores the new hash after a `2xx`.
- If KV can't be read, the Worker forwards (correct, just not free).

## Production today

About 30 membership rows in total across products; Univents has at most
2 events per person. The deepest chain from a URL to a pivot is 3 hops.
Access tokens live 1 hour.

## Migration

One app at a time, in three steps.

1. **Groundwork, before any app trusts a capability:**
   - `lib/go/authz` and the project binding in `lib/go/backend/identityx`
     (both the JWT and the API key paths).
   - IdentityX as the issuer: general capabilities in the token as
     `<level>.<action>` strings, the catalog `PUT` and its edge hash
     (catalog validation accepts `*` as an action), general grants stored
     per project with names as text, and keys (`project_id`,
     `unrestricted`, names as text, the minting rule, `400` on neither).
   - **IdentityX's new endpoints keep today's role checks** (project admin
     via `CheckProject`) until step 3 gives its member rows capabilities.
     `project.writeCapabilities` and `project.manageKeys` take over then.
     The one exception is self-minting, allowed from step 1: key creation
     drops today's `x-scope: platform-only` and the admin-only gate for a
     key whose actor is the caller.
   - **Existing keys keep working:** every key in production has no
     capabilities and today acts as its full actor, so the migration sets
     `unrestricted = true` on all of them. It also fills
     `api_keys.project_id`: from `actors.project_id` for project actors,
     and by hand for the few keys of platform accounts (an app's service
     key gets its app's project). Narrowing a key is a later, deliberate
     edit.
   - The Payssage front sends `unrestricted: true` for wallet keys in the
     same release as the `400`.
2. **The apps, in order:** Informd (one form; add its missing owner row),
   Payssage (add owner rows for personal wallets and collectors),
   Univents with `platform → event` only (org and edition pivots come
   with the planned rework, and slot into the chain then).
3. **IdentityX's own checks last:** `platform_roles` becomes general
   `platform.*` capabilities; org and project members get `capabilities`
   like any pivot.

**Within an app**, in this order:

- Declare **the app's full action set** and its role bundles first, for
  every operation that will move, not just the first one.
- Add `capabilities text[]` to each pivot, drop the `role` CHECK
  constraints (the label now takes any bundle name), and **fill it once** from
  `role` with those bundles (owner → `<level>.*`, admin and staff →
  today's checks as lists of `<level>.<action>`). `role` stays, as a
  label. Filling per operation would leave existing rows without the
  actions of later operations, because new capabilities are opt-in.
- Make every node-creation, member-edit and member-removal path go
  through `access.Create`, `access.Grant` and `access.Remove`.
- Then switch operations to `Can` one by one, and delete each role check
  as it goes.

## Not doing

- Grants on specific nodes stored in IdentityX (a ledger, or hints in
  the token). The fronts ask the app instead. Revisit only if `/me/can`
  turns out to cost more than the round trip it saves.
- Roles defined or edited in IdentityX (custom roles per tenant).
- A central grant store as the source of truth (Zanzibar, SpiceDB).
- Deny rules: access is only ever granted.
- Resources with two parents.
- Grants that cross apps. When one app needs to act on another's resource
  (Univents ticket money in a Payssage wallet), it calls the other app's
  API with a key minted for that purpose, never a shared grant or a
  `Parent` across apps.
