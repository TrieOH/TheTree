# ADR-0023 — Authorization: capabilities, checked up the tree

- **Status:** proposed
- **Date:** 2026-11-18
- **Scope:** `lib/go/authz`, `sdk/go/IdentityX`, `api/{identityx,informd,payssage,univents}`

## Why

Access control was rewritten several times (manual checks, roles,
Zanzibar, back to roles). Today it is about 140 hand-written checks that
ask "is this person staff?", copy the "else the parent's role" logic in
every backend, and load the same rows twice. IdentityX's capabilities
exist but nothing uses them (production: 0 capabilities, 0 assignments).

## The idea

Code never asks *who you are*. It asks **can you do this action here?**

```go
err := access.Can(ctx, "markAttendance", authz.Ref{Kind: "edition", ID: editionID})
```

The operation names only the action. Who may do it, and at which level,
is in the capabilities.

## Capabilities

### Names

A capability is **an action granted at a level**: `<level>.<action>`, or
`<level>.*` for every action at that level. Levels are singular and match
`Ref.Kind` (`platform`, `org`, `event`, `edition`, `program`, …).

Granted at a level, a capability covers that node **and everything below
it**:

| Capability | Covers |
|---|---|
| `program.markAttendance` on `program:P` | program P |
| `edition.markAttendance` on `edition:E` | every program in edition E |
| `event.*` on `event:V` | everything in event V (the event owner) |
| `platform.markAttendance` | every program everywhere (e.g. a moderator) |
| `platform.*` | everything (super admin) |

There is no bare `*`: a wildcard always names its level.

### General and specific

- **Specific:** has `on` — one or more nodes of its level. It lives on an
  app's pivot row, and the app pushes it to IdentityX.
- **General:** has no `on` — **every node of its level**. `platform.*` is
  the case where the level is the root, but any level can be general: a
  company where every writer may write every document gets
  `document.write` with no `on`. General capabilities are assigned in
  IdentityX, to users and API keys.

IdentityX records every capability of both kinds, and all of them go in
the token. There is no other flag.

### The catalog

The app declares each action once, with the levels it can be granted at:

```go
access.Action("markAttendance", "platform", "org", "event", "edition", "program")
```

The catalog it sends to IdentityX holds the derived capabilities
(`platform.markAttendance` … `program.markAttendance`) and each level's
`<level>.*`; nobody writes those by hand. IdentityX rejects a grant whose
name and `on` disagree (`edition.markAttendance` on `event:…`).

**Each app sends its catalog on startup**: an idempotent
`PUT /projects/{project_id}/capabilities` with `If-None-Match: <hash>`. IdentityX's
edge answers `304` when nothing changed, so the container is not woken.
The sync runs in the background and never blocks startup.

## Roles are pivot tables

- A role is **being in a pivot table**: a row in `event_members` makes
  you a member of that event. Each app keeps its pivots, as today.
- **The row stores the capabilities that person has there**, expanded.
  The app offers a default set when the row is created; after that the
  row is the truth.
- **New capabilities are opt-in**: they reach no row until someone grants
  them. Giving one to everyone is a deliberate migration.
- **The owner is the row with `<level>.*`**: `event.*` on their event,
  which covers everything in it, new actions included. `owner_id` columns
  stop deciding access.
- Removing a capability from the catalog removes it from the rows at the
  next startup sync; `Can` ignores unknown names meanwhile.

## The token

The token carries both kinds, trusted differently:

- **General** (no `on`): **trusted.** `Can` grants straight from the
  token, with no database.
- **Specific** (with `on`): **a hint, never trusted alone.** It tells
  `Can` which pivot row to look at, and one query on that row confirms
  it. A stale hint (revoked, or changed since the token was issued) fails
  the confirmation and `Can` falls back to the climb; a missing hint
  (granted after the token was issued) also falls back to the climb.
  Either way the app's pivot decides.

## The levels

Every app has the same shape: a **platform** level at the top, then its
own levels, each with an optional pivot.

| App | Levels (top → bottom) |
|---|---|
| IdentityX | platform → org → project |
| Payssage | platform → org → wallet |
| Informd | platform → namespace → form |
| Univents | platform → org → event → edition |

The **platform** level is always the token: no database.

## How `Can` decides

In `lib/go/authz`, the same for every app. `Can(ctx, action, at)`:

1. **Free checks, from the token:** a general `platform.<action>` /
   `platform.*`, or a general `<at.Kind>.<action>` / `<at.Kind>.*`.
2. **A ref with no id** (`authz.Platform`, or `Ref{Kind: "document"}` for
   "any document") stops here: only general capabilities apply to it.
3. **The chain:** from `at` up to the platform, through the app's `Parent`
   (e.g. `[edition:E, event:V, org:O]`).
4. **At each level of the chain, bottom up:** a general
   `<level>.<action>` / `<level>.*` in the token (trusted), or a specific
   one whose `on` names that node (a hint, confirmed with one query on
   the pivot row).
5. **The climb:** the pivots at each level, bottom up, for grants newer
   than the token.
6. Nothing → `403`.

General capabilities of a level are checked inside the chain, not before
it: `org.markAttendance` must not reach a personal event that sits in no
org, and only the chain knows which levels a node is under.

```go
func (c *Checker) Can(ctx context.Context, action string, at Ref) error {
    tok := idx.CapabilitiesFrom(ctx)
    if tok.General(names(Platform, action)...) || tok.General(names(at, action)...) {
        return nil
    }
    if at.ID == uuid.Nil {
        return ErrForbidden
    }
    chain, err := c.chain(ctx, at)
    if err != nil {
        return err
    }
    for _, ref := range chain {
        if tok.General(names(ref, action)...) {
            return nil
        }
        if tok.HasOn(names(ref, action), ref) {
            if ok, err := c.holds(ctx, tok.Subject, ref, action); err != nil || ok {
                return err
            }
        }
    }
    for _, ref := range chain {
        if ok, err := c.holds(ctx, tok.Subject, ref, action); err != nil || ok {
            return err
        }
    }
    return ErrForbidden
}

// what counts at a level: "edition.markAttendance" or "edition.*"
func names(ref Ref, action string) []string {
    return []string{ref.Kind + "." + action, ref.Kind + ".*"}
}
```

## What each app writes

Two functions and nothing else:

```go
// Who is above this node?
Parent(ctx context.Context, ref authz.Ref) (authz.Ref, error)
// Which capabilities does this person have at this node? (their pivot row there)
Capabilities(ctx context.Context, who uuid.UUID, ref authz.Ref) ([]string, error)
```

Each is a `switch` with one case per level, calling the repos it already
has.

## IdentityX is the ledger

- When an app grants or revokes something on a pivot, it also pushes it
  to IdentityX (idempotent). IdentityX records every grant and puts them
  in the token.
- **The app is the source; IdentityX is the copy.** The backend never
  decides specific access from the ledger alone, so drift can't let
  anyone in: at worst the front shows a button that returns `403` until
  the next push or refresh. Revocation is immediate, because the backend
  checks its own pivot.
- Fronts read the whole token to show or hide things. No `/me/access`.

### Sending specific capabilities

The unit is **one pivot row**: a person's full capability list on one
resource. The app sends it whole, so a push is a replace and naturally
idempotent.

```
PUT /projects/{project_id}/actors/{actor_id}/capabilities/{kind}/{id}
{ "capabilities": ["edition.markAttendance", "edition.checkIn"], "as_of": "2026-11-18T03:01:02Z" }
```

- An empty list removes them. Deleting a resource removes every
  capability on it: `DELETE /projects/{project_id}/resources/{kind}/{id}/capabilities`.
- `as_of` is the pivot row's `updated_at`; IdentityX ignores a push older
  than what it has, so out-of-order pushes can't undo a newer one.
- The app pushes **after its transaction commits**, through the SDK, with
  a few retries. A push that still fails is logged and only leaves the
  ledger behind for a while: the front may be off, access is not.
- The call uses the app's service API key, with `project.writeCapabilities` on its own project (IdentityX's own
  levels are platform → org → project); an app can't write another
  project's. General capabilities keep being assigned in IdentityX, as
  today.

```go
// sdk/go/IdentityX
client.Capabilities.Put(ctx, actorID, idx.Ref{Kind: "edition", ID: editionID}, caps, row.UpdatedAt)
client.Capabilities.DeleteResource(ctx, idx.Ref{Kind: "event", ID: eventID})
```

### The token

`subject.capabilities` is a list of entries. An entry with `on` is
specific; one without is general:

```json
{
  "subject": {
    "id": "01a0…", "project_id": "01a0…", "type": "human", "email": "ana@…",
    "capabilities": [
      { "name": "platform.markAttendance" },
      { "name": "edition.markAttendance", "on": ["edition:7f3a…", "edition:b21c…"] },
      { "name": "edition.checkIn",        "on": ["edition:7f3a…"] },
      { "name": "event.*",                "on": ["event:19c2…"] }
    ]
  }
}
```

- An actor belongs to one project, so its token only carries that
  project's (that app's) capabilities.
- API keys get the same shape: their general capabilities, and specific
  ones if an app gives the key any.
- Every refresh rebuilds `capabilities` from the ledger.
- **Safety valve:** past a size limit (e.g. 200 specific entries),
  IdentityX leaves the specific entries out and sets
  `"capabilities_truncated": true`. Only the hints are lost: `Can` climbs
  instead.

### Reading capabilities (SDK)

The SDK's auth middleware already decodes the token into the context; the
capabilities come with it:

```go
c := idx.CapabilitiesFrom(ctx)
c.General("platform.createEvent")              // bool — trusted
c.On("edition.markAttendance")                 // []Ref — where it is granted (a hint)
```

`lib/authz.Can` reads these itself; app code rarely needs to.

For screens that list people (who is staff of this edition?), the app
reads its own pivot. IdentityX also answers it from the ledger, for its
admin screen:

```go
client.Capabilities.ListActor(ctx, actorID)                         // everything one person holds
client.Capabilities.ListResource(ctx, idx.Ref{Kind: "edition", ID: editionID}) // everyone on one resource
```

## IdentityX API

Everything is per project (one project = one app). The existing
`/projects/{project_id}/capabilities` resource becomes the catalog.

| Method and path | What | Called by |
|---|---|---|
| `GET /projects/{project_id}/capabilities` | the catalog | apps, IdentityX's admin screen |
| `PUT /projects/{project_id}/capabilities` | replace the catalog; `If-None-Match: <hash>` → `304` at the edge | the app, on startup |
| `GET /projects/{project_id}/actors/{actor_id}/capabilities` | everything one actor holds, general and specific | admin screens |
| `PUT /projects/{project_id}/actors/{actor_id}/capabilities` | replace an actor's **general** capabilities | IdentityX's admin screen |
| `PUT /projects/{project_id}/actors/{actor_id}/capabilities/{kind}/{id}` | replace an actor's **specific** capabilities on one node; `[]` removes; `as_of` orders pushes | the app, after its pivot changes |
| `GET /projects/{project_id}/resources/{kind}/{id}/capabilities` | who holds what on one node | admin screens |
| `DELETE /projects/{project_id}/resources/{kind}/{id}/capabilities` | drop every capability on a deleted node | the app, after deleting it |
| `PUT /projects/{project_id}/api-keys/{key_id}/capabilities` | replace an API key's capabilities (general and specific, same entries as the token) | whoever manages the key |

Writes need `project.writeCapabilities` on that project: the app's own
service key, or a project admin. The old `POST` that created one
capability goes away; the catalog is only ever replaced whole.

## Data types

Three pieces of code meet in every check: the IdentityX SDK, `lib/authz`
and the app. They share **one** set of types, defined in the SDK, so no
layer converts between its own versions.

**Strings on the wire** (JSON, token, database):

| Thing | Form | Example |
|---|---|---|
| level | singular, lower case | `edition` |
| action | lowerCamel | `markAttendance` |
| capability | `<level>.<action>` or `<level>.*` | `edition.markAttendance` |
| node | `<level>:<uuid>` | `edition:7f3a…` |

**`sdk/go/IdentityX` (package `idx`): the wire and the token**

```go
type Ref struct {
    Kind string    // a level
    ID   uuid.UUID // zero = "any node of this level"
}                  // JSON: "edition:7f3a…"

type Capability struct {
    Name string `json:"name"`         // "edition.markAttendance"
    On   []Ref  `json:"on,omitempty"` // empty = general
}

type Capabilities []Capability // subject.capabilities

func (c Capabilities) General(names ...string) bool          // trusted
func (c Capabilities) HasOn(names []string, ref Ref) bool     // a hint
func (c Capabilities) On(name string) []Ref

type Action struct { // a catalog entry
    Name   string   `json:"action"` // "markAttendance"
    Levels []string `json:"levels"` // ["platform", "event", "edition", "program"]
}

func CapabilitiesFrom(ctx context.Context) Capabilities
// client.Capabilities.PutCatalog / Put / DeleteResource / ListActor / ListResource
```

**`lib/go/authz`: the check**

```go
type Ref = idx.Ref // the same type, aliased: apps never convert
var Platform = Ref{Kind: "platform"}

type Lookup interface {
    Parent(ctx context.Context, ref Ref) (Ref, error)
    Capabilities(ctx context.Context, who uuid.UUID, ref Ref) ([]string, error) // full names
}

type Checker struct{ /* lookup, actions */ }
func New(l Lookup, actions ...idx.Action) *Checker
func (c *Checker) Can(ctx context.Context, action string, at Ref) error
func (c *Checker) Catalog() []idx.Action // what the startup sync sends
var ErrForbidden = ErrInsufficientRole   // still 403 through the shared mapper
```

`lib/authz` knows no app's levels or tables: only strings, `Ref` and the
`Lookup` it is given.

**The app: its levels, actions and pivots**

```go
// univents/internal/access
const (Platform = "platform"; Org = "org"; Event = "event"; Edition = "edition"; Program = "program")
const MarkAttendance = "markAttendance"

var Checker = authz.New(lookup{…},
    idx.Action{Name: MarkAttendance, Levels: []string{Platform, Org, Event, Edition, Program}},
)

// models: the pivot row stores full names
type EventMember struct {
    EventID, UserID uuid.UUID
    Capabilities    []string  // text[]: "event.*", "event.markAttendance"
    UpdatedAt       time.Time
}
```

The app's `Capabilities` returns the row's list as is. When the row
changes, the service writes it, commits, and pushes the same list with
`client.Capabilities.Put(ctx, userID, authz.Ref{Kind: access.Event, ID: eventID}, row.Capabilities, row.UpdatedAt)`.

## Not authorization

Business rules stay in the services: ticket access levels, staff-only
programs, "needs a confirmed ticket". Reading someone else's membership
for such a rule (e.g. "is this attendee staff?") uses the same
`Capabilities` function, not `Can`.

Records that belong to their holder (`purchaser_id`, `user_id`) are
checked in the operation.

## Not in the spec

The spec keeps authentication (`security`, `x-scope`) only. Permissions
live in the code, one `Can` line per operation, so nothing can fall out
of sync.

## Production today

About 30 membership rows in total across products; Univents has at most
2 events per person. The deepest chain from a URL to a pivot is 3 hops.

## Migration

- **All:** add a `capabilities` column to each pivot and fill it from the
  current role (owner → `<level>.*`, admin and staff → today's checks as
  lists of `<level>.<action>`).
- **Payssage:** add owner rows for personal wallets and collectors.
- **Informd:** add the missing owner row for its one form.
- **IdentityX:** the catalog `PUT`, the grants ledger (general and
  specific) and the token claims.
- **Univents:** org and edition pivots come with the planned rework.

## Not doing

- Roles defined or edited in IdentityX (custom roles per tenant).
- A central grant store as the source of truth (Zanzibar, SpiceDB).
- Deny rules: access is only ever granted.
- Resources with two parents.
