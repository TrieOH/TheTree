status: accepted

summary: IdentityX creates and rotates an encryption key for every project alongside its signing key, so it's ready when project data gets encrypted.
scope:
  - api/identityx/internal/keys

  - api/identityx/internal/services/{projects,organizations}

## Why

The key module (`internal/keys`) creates and rotates two keys for every scope through one `Ensure` call: a signing key (Ed25519) and an encryption key (RSA-4096). The signing key is used to mint and verify JWTs. The encryption key isn't used by anything. Every secret IdentityX stores today, like OAuth client secrets and provider tokens, is sealed with the master key (`ENCRYPTION_KEY`, read by `lib/crypto.MasterKey()`).

An architecture review noticed this and suggested creating signing keys only. We kept both for two reasons:

1. **It has a planned user.** The encryption key is for project data that must stay private to one tenant, even from other tenants' keys. One platform-wide master key can't do that. When that feature lands, it should find a key that already exists, already rotates and can already be retired, instead of backfilling one for every project.
2. **Two paths drift.** Two ways of creating the same keys already drifted once: one set no expiry, another hardcoded 7 days, and a third created nothing. One lifecycle for both keys means one rule and one set of tests. Adding encryption keys later through a second path would invite the same drift.

## Decision

The key module keeps creating and rotating both keys for every scope, on the same schedule, through the same call. The encryption key is held for per-project data encryption on purpose. Retired keys stay rejected for both types. Secrets at rest stay sealed with the master key until project-data encryption exists.

## Consequences

- Each scope rotates two keys per `KeyLifetime`, including an RSA-4096 keygen nobody reads yet. The rotation schedule bounds that cost, and we accept it.
- When project-data encryption lands, it uses `keys.Ensure` and the repo port instead of making its own keys.
- If it never lands, the encryption half stays unused and a later review can drop it. This ADR records why, so that review doesn't have to work it out again.
