# ADR-0006 — Per-project encryption keys are provisioned and rotated despite no consumer today

- **Status:** accepted
- **Date:** 2026-08-15
- **Scope:** `api/identityx/internal/keys`, `api/identityx/internal/repos/crypto_keys`, `api/identityx/internal/services/{projects,organizations}`

## Context

The Key-lifecycle module (`internal/keys`) provisions and rotates two key types per
scope — signing (Ed25519) and encryption (RSA-4096) — under one symmetric `Ensure`
interface. The signing key is consumed: the Token-lifecycle module mints and verifies
JWTs with it. The encryption key is not: today, every secret at rest in IdentityX —
OAuth client secrets and provider tokens — is sealed with the *master key*
(`ENCRYPTION_KEY` env via `lib/crypto.MasterKey()`), not with the per-project
encryption key. An architecture review flagged this: the encryption key fails the
deletion test (delete it and nothing reappears), and suggested provisioning signing
keys only.

Two facts keep the symmetric lifecycle:

1. **Planned consumer.** The per-project encryption key exists to encrypt *project
   data* — data whose confidentiality must be scoped to one tenant and protected even
   from other tenants' keys, which the platform-wide master key cannot express. When
   that consumer lands (envelope encryption of project-scoped payloads), it must find
   a key that already exists, already rotates on a real schedule, and already has a
   retirement story — not a key that has to be backfilled for every existing project.
2. **Drift risk.** Two provisioning paths for the same concept already drifted once
   (`ExpiresAt: nil` vs a hardcoded 7 days, plus a path that provisioned nothing).
   Symmetric lifecycle means one policy, one seam, one test surface; a second,
   deferred provisioning path for encryption keys would recreate the same drift.

## Decision

The Key-lifecycle module provisions and rotates signing **and** encryption keys for
every scope, symmetrically, on the same schedule and through the same interface. The
encryption key is a deliberate reservation for per-project data encryption, not dead
provisioning. Verification keeps rejecting `retired` keys for both types' lifecycle
purposes; the master key remains the seal for secrets at rest until the project-data
consumer exists.

## Consequences

- Ongoing rotation work with no reader: each scope rotates two keys (RSA-4096 keygen
  included) per `KeyLifetime`. The cost is bounded by the rotation schedule and is
  accepted as the price of a ready lifecycle.
- When the project-data encryption consumer lands, it crosses the Key-lifecycle seam
  (`keys.Ensure` / the repo port) instead of minting its own keys — the interface is
  already the test surface.
- If the consumer never arrives, the encryption half stays unused; the next
  architecture review may revisit this decision and drop it via the deletion test. The
  reservation is recorded here so that review does not have to re-derive the context.
