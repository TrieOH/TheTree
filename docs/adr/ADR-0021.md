# ADR-0021 — A feature's spec lives in its folder

- **Status:** accepted
- **Date:** 2026-11-17
- **Scope:** `tools/go/problemgen`, `api/{identityx,informd,payssage,univents}` (`api-spec.yml`, `problems.yml`, `internal/features/*/spec.yml`), `.husky`

## Context

ADR-0015 made a feature one folder: its repo, handlers and operations sit
together. Its contract did not move with it. Each Backend's spec was one
file (Univents' was 4,940 lines, IdentityX's 3,060), and its problems were
one more (`problems.yml`). Adding an operation meant editing the feature
folder, the middle of a large shared file and a second shared file, and
reviewing a feature meant reading three places.

## Decision

- **Each feature has a `spec.yml`** at `internal/features/<name>/spec.yml`:
  the path items it serves, the components only it uses, and the problems
  only it answers. It is a fragment, not a document: `paths` and
  `components`, nothing else.
- **`api-spec.yml` imports the paths with ordinary OpenAPI refs**, one
  per path, in the order the spec lists them:

  ```yaml
  paths:
    /wallets:
      $ref: './internal/features/wallets/spec.yml#/paths/~1wallets'
  ```

  It keeps what is not a feature's: `info`, `servers`, security, tags, the
  harness routes and the components several features share. A feature
  reaches those with relative refs
  (`../../../api-spec.yml#/components/schemas/UUID`), so editors and
  linters resolve the split spec like any multi-file OpenAPI document.
- **`tools/problemgen` bundles it.** It inlines each imported path item,
  merges every reached file's components under their own names, and
  leaves only local refs; `api-spec.gen.yml` stays the one spec codegen,
  orval and `/docs/openapi.yml` read. It fails on a ref that names no
  component, a component two files declare, a path imported under another
  key, and a feature path the spec never imports.
- **Problems follow the same rule.** A problem answered only by one
  feature is declared in that feature's `spec.yml`; one answered across
  features stays in the Backend's `problems.yml`, and the shared ones in
  `api/problems.yml`. A problem's authored name never reaches the bundle,
  so it may share a plain schema's name.
- The hooks treat a feature's `spec.yml` and a Backend's `problems.yml`
  like `api-spec.yml`: staging one checks the TS client and the fronts
  importing it.

## Consequences

- A feature's contract is reviewed with its code. Adding an operation
  touches its feature folder and one line of `api-spec.yml`.
- The split is enforced at build time: a feature path no one imports fails
  `just gen`, so a spec can't silently lose an operation.
- Splitting kept the bundle identical, key for key; only the order of
  problems sharing a status (the `oneOf` of a `Status<N>Problem`) changed,
  which nothing reads.
- Shared components stay in `api-spec.yml`. A component moves into a
  feature only when that feature alone uses it.
