## Why

ADR-0015 made a feature one folder holding its repo, handlers and operations. Its contract didn't move with it. Each backend's spec was one file (Univents' was 4,940 lines, IdentityX's 3,060), and its problems were in another (`problems.yml`). Adding an operation meant editing the feature folder, the middle of a huge shared file and a second shared file, and reviewing a feature meant reading three places.

## Decision

- **Each feature has a `spec.yml`** at `internal/features/<name>/spec.yml` with the paths it serves, the components only it uses, and the problems only it returns. It's a fragment, not a full document: just `paths` and `components`.
- **`api-spec.yml` imports the paths with normal OpenAPI refs,** one per path, in the spec's order:

  ```yaml
  paths:
    /wallets:
      $ref: './internal/features/wallets/spec.yml#/paths/~1wallets'
  ```

  It keeps what doesn't belong to one feature: `info`, `servers`, security, tags, the harness routes and the components several features share. A feature reaches those with relative refs (`../../../api-spec.yml#/components/schemas/UUID`), so editors and linters read the split spec like any multi-file OpenAPI document.
- **`tools/problemgen` bundles it.** It inlines each imported path, merges every file's components under their own names, and leaves only local refs. `api-spec.gen.yml` is still the one spec codegen, orval and `/docs/openapi.yml` read. It fails on a ref to a component that doesn't exist, a component declared in two files, a path imported under another key, and a feature path the spec never imports.
- **Problems follow the same rule.** A problem only one feature returns is declared in that feature's `spec.yml`. One returned across features stays in the backend's `problems.yml`, and the shared ones in `api/problems.yml`. A problem's name in YAML never reaches the bundle, so it can share a name with a plain schema.
- **The git hooks treat a feature's `spec.yml` and a backend's `problems.yml` like `api-spec.yml`:** staging one checks the TS client and the fronts that import it.

## Consequences

- A feature's contract is reviewed with its code. Adding an operation touches its folder and one line of `api-spec.yml`.
- The split is enforced at build time: a feature path nobody imports fails `just gen`, so a spec can't quietly lose an operation.
- Splitting kept the bundle identical, key for key. Only the order of problems sharing a status (the `oneOf` in a `Status<N>Problem`) changed, and nothing reads that order.
- Shared components stay in `api-spec.yml`. A component moves into a feature only when that feature alone uses it.
