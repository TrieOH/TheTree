# ADR-0014 — Backends boot from shared modules and one explicit Deps

- **Status:** accepted
- **Date:** 2026-10-23
- **Scope:** `lib/go` (new backend kit), `api/{identityx,informd,payssage,univents}/cmd`, `api/*/internal/app`

## Context

Reading how a Backend starts is the hardest part of the codebase. The
Harness (ADR-0001, ADR-0008, ADR-0009) owns the process lifecycle, but
everything inside the start hook is hand-written per Backend, and it has
grown convoluted:

- **The order is implicit.** Univents' start hook runs about 14 steps in
  one closure — IdentityX client, object storage, email, Payssage client, a
  network wallet check, the pool, the notifier, the tx runner, repos, jobs,
  operations, middlewares, handlers, router. Nothing says which step needs
  which.
- **Hidden coupling through mutated fields.** `app.db` and `app.idxClient`
  are assigned inside the closure and read later by `setupAuthMiddlewares`;
  moving one line breaks boot with nothing in the code saying why.
- **Globals installed during boot.** Payssage fills the package-level
  `PayssageProviders` map; IdentityX installs `setup.UseProbe`. Their readers
  do not show where the values come from.
- **The same infrastructure, wired four slightly different ways.** The
  IdentityX auth primitives exist four times and drifted: Payssage's copy
  hardcoded `http://identityx:8080` for API-key introspection, which broke
  Univents' boot after the Cloudflare move. `initJobs`, `ToRateLimit` and
  the database setup are copied too.
- **Config handed over twice.** `Boot` and `NewRouter` each receive their
  own config with the same app name, CORS, spec and rate limit.
- **Two failure paths.** `Boot` returns errors, but `CreateRouter` calls
  `errx.Exit` from inside wiring.
- **Hand-written shutdown.** Each start hook returns a closure that undoes
  whatever it opened, and each error branch must remember to close the pool.
- **Long positional constructors** (Univents' `services.NewOperations` takes
  12 arguments) and dead helpers (`SetupIdentityX` in Informd and Univents).

A DI framework would remove the wiring code but not the problem: uber/fx
resolves the graph by reflection at runtime, which hides the order, and
google/wire generates code that still has to be read. The goal is
readability, so the fix stays in plain Go.

## Decision

- **A backend kit in `lib/go`** with one entry point, `backend.Run(App)`,
  that replaces `httpserver.Boot` and the per-Backend router assembly.
  `App` declares the name, the OpenAPI spec, the server settings (port,
  CORS, rate limit), the modules and a `Build` function.
- **Shared infrastructure is a module.** A module opens one piece of
  infrastructure, fills its field of `Deps`, and registers its close. The
  first set:
  - `postgres` — pool, tx runner, constraint messages; no migrations
    (`just <svc>-goose` owns the schema).
  - `identityx` — the SDK client and every auth primitive (JWT, API key via
    introspect at `IDENTITY_X_URL`, any), built once for the Backends that
    consume IdentityX. Per-Backend tweaks are module options (Univents'
    `RequireVerifiedEmail`). IdentityX itself issues the tokens, so it does
    not list this module and supplies its own primitives.
  - `email` — the SMTP sender (IdentityX and Univents).
  - `jobs` — the carrier picked by `JOBS_URL`, available in `Deps.Jobs` from
    the start (so handlers can enqueue, e.g. Payssage's redrive). The
    registry depends on repos and services that only exist in `Build`, so
    `Build` hands it over with `d.Jobs.Serve(registry, periodic...)`; the
    module mounts `/_jobs` or starts the in-process runner then.
  - The router frame is part of the kit, fed from the same config: CORS,
    rate limit, `/health`, `/docs/openapi.yml`, and `/_jobs` when the jobs
    module is listed.
- **Modules run in the listed order and close in reverse.** No dependency
  sorting: the list in `main` is the order, and reading it is how you learn
  it. A module that needs another comes after it.
- **One explicit `Deps` struct** with plain fields (`DB`, `Tx`, `IDX`,
  `Email`, `Jobs`, …); a module that is not listed leaves its field nil.
  Nothing is assigned onto an app struct after the fact.
- **The Backend writes only what is its own:** its config struct, its
  constraint messages, and `Build(ctx, deps, router) error`, which wires
  its features. Backend-specific boot steps — Univents' wallet check,
  IdentityX's key provisioning, Payssage's provider registry — are ordinary
  code in `Build` that returns errors. Modules are only for infrastructure
  two or more Backends share.
- **No boot-time globals.** The provider registry and the setup probe
  become values passed to the code that uses them.
- **One failure path.** Every step returns an error to `Run`; `errx.Exit`
  stays in `cmd/main` only.
- **Constructors take `Deps`-style structs**, not long positional lists.
- **`Build` receives the router; it does not return one.** The kit hands
  `Build` a context (boot steps like key provisioning and the wallet check
  need one) and the router frame. `Build` gets its per-operation auth
  chains from `d.Chains(primitives)` — `d.IDX.Auth` for IdentityX's
  consumers, its own primitives for IdentityX — and mounts the strict
  server with `httpserver.MountStrict` and its own generated constructors
  (the kit never imports a Backend's `openapi` package), plus any raw
  routes. There is no router options struct.
- **The auth resolver keeps only its core.** It reads each operation's
  `security` in the spec (JWT, API key, either, none) and builds the
  chains, so handlers never check authentication themselves. The setup
  guard and the `x-scope` checkers are removed: "platform-only" becomes a
  service check (`CheckPlatform` already exists), and "only setup works
  until setup is done" becomes a check in IdentityX's own code. Trade-off:
  both were fail-closed and validated at boot; as service logic a missing
  check is not caught automatically, so IdentityX's tests must cover them.
  Acceptable while IdentityX is their only user.
- **Raw routes stay outside the spec, documented on purpose.** OpenAPI can
  describe a WebSocket handshake (a `GET` answering 101) but not the
  messages after the upgrade, nor the JSON-RPC methods behind an MCP
  endpoint; oapi-codegen's strict server cannot hijack a connection or
  stream SSE either. WebSocket, SSE and MCP handlers are mounted raw in
  `Build`, and listed in the spec's description block (an AsyncAPI document
  for message contracts when one is worth writing).

## Worked examples

Sketches, not compiled; names are illustrative.

IdentityX — the token issuer, so no `identityx` module:

```go
func main() {
	cfg := config.Load()
	errx.Exit(backend.Run(backend.App{
		Name:   "identityx",
		Spec:   spec.OpenAPISpec,
		Server: cfg.Server,
		Modules: []backend.Module{
			postgres.Module(cfg.Postgres, constraintMessages()),
			email.Module(cfg.SMTP),
			jobs.Module(cfg.JobsURL),
		},
		Build: build(cfg),
	}), "identityx exited with error")
}

func build(cfg config.Config) backend.BuildFunc {
	return func(ctx context.Context, d backend.Deps, r chi.Router) error {
		repos := repos.New(sqlc.New(d.DB))

		keys := keys.NewManager(repos.CryptoKeys, repos.Projects, cfg.KeyPolicy())
		err := keys.EnsureAll(ctx) // every scope has keys before traffic
		if err != nil {
			return fmt.Errorf("ensure crypto keys: %w", err)
		}

		tokens := tokens.NewManager(repos, keys, cfg.TokenPolicy())
		actionTokens := tokens.NewActionTokenManager(repos.ActionTokens, cfg.ActionTokenPolicy())
		setupState := setup.NewState(repos.Actors) // was the global setup.UseProbe

		d.Jobs.Serve(jobs.Registry(jobs.Deps{Repos: repos, ActionTokens: actionTokens, Keys: keys, Email: d.Email}),
			jobs.Periodic(cfg.RotateKeysJobDuration)...)

		ops := services.New(services.Deps{
			Repos: repos, Tx: d.Tx, Jobs: d.Jobs, Keys: keys,
			Tokens: tokens, ActionTokens: actionTokens, Setup: setupState,
			HmacSecret: cfg.HmacSecret, AppURL: cfg.AppURL,
		})

		chains := d.Chains(authPrimitives(ops, tokens))
		mountStrict(r, handlers.NewServer(ops), chains)
		return nil
	}
}
```

Univents — Univents-only infrastructure stays in `Build`:

```go
func main() {
	cfg := config.Load()
	errx.Exit(backend.Run(backend.App{
		Name:   "univents",
		Spec:   spec.OpenAPISpec,
		Server: cfg.Server,
		Modules: []backend.Module{
			postgres.Module(cfg.Postgres, constraintMessages()),
			identityx.Module(cfg.IdentityX, identityx.RequireVerifiedEmail(cfg.RequireVerifiedEmail)),
			email.Module(cfg.SMTP),
			jobs.Module(cfg.JobsURL),
		},
		Build: build(cfg),
	}), "univents exited with error")
}

func build(cfg config.Config) backend.BuildFunc {
	return func(ctx context.Context, d backend.Deps, r chi.Router) error {
		storage, err := objectstorage.New(ctx, cfg.ObjectStorage)
		if err != nil {
			return err
		}
		pay := payssage.New(cfg.Payssage)
		_, err = pay.GetWallet(ctx, cfg.PayssageWalletID) // fail fast (D6)
		if err != nil {
			return fmt.Errorf("payssage platform wallet check failed: %w", err)
		}
		notifier := database.NewNotifier(cfg.Postgres.DSN())

		repos := repos.New(sqlc.New(d.DB))

		d.Jobs.Serve(jobs.Registry(jobs.Deps{Repos: repos, Email: d.Email, Notifier: notifier, Tx: d.Tx}))

		ops := services.New(services.Deps{
			Repos: repos, Tx: d.Tx, Jobs: d.Jobs, IDX: d.IDX, Email: d.Email,
			Storage: storage, Payssage: pay, WalletID: cfg.PayssageWalletID,
			Notifier: notifier, HmacSecret: cfg.HmacSecret, WebhookSecret: cfg.PayssageWebhookSecret,
		})

		h := handlers.NewServer(ops)
		mountStrict(r, h, d.Chains(d.IDX.Auth))

		// Raw routes: outside the spec on purpose.
		r.Get("/editions/{edition_id}/store/stream", h.ServeStoreStream)
		r.Handle("/ws", http.HandlerFunc(h.ServeWS))
		return nil
	}
}
```

Univents' boot today spans `app.go`, `wire.go`, `router.go`, `auth.go` and
`clients.go` (about 450 lines); here it is `main` plus `build`, with no
hand-written shutdown.

## Rollout

1. Build the kit next to `httpserver.Boot`, without changing it.
2. Move the IdentityX auth primitives into the kit first: the largest
   copy, and the one that already caused a production bug.
3. Convert Informd (smallest boot, no jobs) as the pilot; compare the
   before/after boot code.
4. Convert Payssage, Univents and IdentityX, one PR each; IdentityX's
   conversion moves the setup guard and `x-scope` checks into its services.
5. Delete the old `Boot` path and the per-Backend router assembly.

## Consequences

- A Backend's boot is `main` plus `Build`; shared behavior is fixed in one
  place, so a fix like the introspect URL lands once for all four.
- Tests build a `Deps` by hand (test database, fakes) and call `Build`,
  instead of re-assembling routers in per-Backend helpers.
- A Backend that needs infrastructure no other Backend uses opens it in
  `Build`; it becomes a module only when a second Backend needs it.
- `Deps` grows a field per module. If it outgrows plain fields, revisit —
  but not before.
