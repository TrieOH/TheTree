## Why

How a backend starts was the hardest part of the codebase to read. The harness (ADR-0001, ADR-0008, ADR-0009) ran the process, but everything inside the start hook was written by hand per backend, and it had grown tangled:

- **The order was implicit.** Univents' start hook ran about 14 steps in one closure: IdentityX client, object storage, email, Payssage client, a wallet check, the pool, the notifier, the tx runner, repos, jobs, operations, middlewares, handlers, router. Nothing said which step needed which.
- **Fields set in one place were read in another.** `app.db` and `app.idxClient` were set inside the closure and read later by `setupAuthMiddlewares`. Moving one line broke boot, and nothing in the code said why.
- **Boot installed globals.** Payssage filled the package-level `PayssageProviders` map, and IdentityX installed `setup.UseProbe`. Their readers didn't show where the values came from.
- **The same infrastructure was wired four slightly different ways.** The IdentityX auth setup existed four times and had drifted. Payssage's copy hardcoded `http://identityx:8080` for API key checks, which broke Univents' boot after the move to Cloudflare. `initJobs`, `ToRateLimit` and the database setup were copied too.
- **Config was passed twice.** `Boot` and `NewRouter` each got their own config with the same app name, CORS, spec and rate limit.
- **Two ways to fail.** `Boot` returned errors, but `CreateRouter` called `errx.Exit` from inside wiring.
- **Shutdown was hand-written.** Each start hook returned a closure undoing what it opened, and each error branch had to remember to close the pool.
- **Long constructors and dead code.** Univents' `services.NewOperations` took 12 arguments, and `SetupIdentityX` was unused in Informd and Univents.

A dependency injection framework would remove the wiring code but not the problem. uber/fx works out the order at runtime by reflection, which hides it. google/wire generates code that you still have to read. The goal is code you can read, so the fix stays in plain Go.

## Decision

- **A backend kit in `lib/go`** with one entry point, `backend.Run(App)`, replacing `httpserver.Boot` and each backend's router setup. `App` holds the name, the OpenAPI spec, the server settings (port, CORS, rate limit), the modules and a `Build` function.
- **Shared infrastructure is a module.** A module opens one thing, fills its field in `Deps` and registers how to close it. The first ones:
  - `postgres`: the pool, the tx runner and the constraint messages. No migrations; `just <svc>-goose` owns the schema.
  - `identityx`: the SDK client and every auth primitive (JWT, API key checked at `IDENTITY_X_URL`, either), built once for every backend that uses IdentityX. Per-backend differences are options, like Univents' `RequireVerifiedEmail`. IdentityX issues the tokens itself, so it doesn't use this module and supplies its own primitives.
  - `email`: the SMTP sender, for IdentityX and Univents.
  - `jobs`: the carrier picked by `JOBS_URL`, in `Deps.Jobs` from the start so handlers can enqueue. The job registry needs repos and services that only exist inside `Build`, so `Build` hands it over with `d.Jobs.Serve(registry, periodic...)`, and the module then mounts `/_jobs` or starts the in-process runner.
  - The router frame is part of the kit and uses the same config: CORS, rate limit, `/health`, `/docs/openapi.yml`, and `/_jobs` when the jobs module is listed.
- **Modules start in the order listed and close in reverse.** No dependency sorting: the list in `main` is the order, and reading it is how you learn it. A module that needs another comes after it.
- **One `Deps` struct with plain fields** (`DB`, `Tx`, `IDX`, `Email`, `Jobs` and so on). A module that isn't listed leaves its field nil. Nothing is set on an app struct after the fact.
- **The backend writes only its own parts:** its config struct, its constraint messages, and `Build(ctx, deps, router) error`, which wires its features. Boot steps only one backend has, like Univents' wallet check, IdentityX's key setup or Payssage's provider registry, are ordinary code in `Build` that returns errors. Modules are only for infrastructure two or more backends share.
- **No globals set during boot.** The provider registry and the setup probe become values passed to the code that uses them.
- **One way to fail.** Every step returns an error to `Run`. Only `cmd/main` calls `errx.Exit`.
- **Constructors take a struct,** not a long list of arguments.
- **`Build` gets the router; it doesn't return one.** The kit passes `Build` a context, since key setup and the wallet check need one, and the router frame. `Build` gets its auth chains from `d.Chains(primitives)`, using `d.IDX.Auth` in IdentityX's consumers and its own primitives in IdentityX. It mounts the strict server with `httpserver.MountStrict` and its own generated constructors, so the kit never imports a backend's `openapi` package, plus any raw routes. There's no router options struct.
- **The auth resolver keeps only its core.** It reads each operation's `security` in the spec (JWT, API key, either, none) and builds the chains, so handlers never check authentication themselves. The setup guard and the `x-scope` checkers come out of the resolver. "Platform-only" becomes a check in the service, with the existing `CheckPlatform`. "Only setup works until setup is done" becomes a check in IdentityX's own code. The trade-off: both used to fail closed and were checked at boot. As service code, a missing check isn't caught automatically, so IdentityX's tests have to cover them. That's fine while IdentityX is their only user.
- **Raw routes stay outside the spec, on purpose.** OpenAPI can describe a WebSocket handshake (a `GET` that answers 101) but not the messages after it, and not the JSON-RPC methods behind an MCP endpoint. oapi-codegen's strict server can't take over a connection or stream SSE either. WebSocket, SSE and MCP handlers are mounted directly in `Build` and listed in the spec's description, with an AsyncAPI document for their messages when one is worth writing.

## Examples

Sketches, not compiled. Names are illustrative.

IdentityX issues tokens, so it has no `identityx` module:

```go
func main() {
	cfg := config.Load()
	errx.Exit(backend.Run(backend.App{
		Name:   "identityx",
		Spec:   spec.OpenAPISpec,
		Server: cfg.Server,
		Modules: []backend.Module{
			postgres.Module(cfg.Postgres, constraintMessages()),
			email.Module(cfg.SMTP),
			jobs.Module(cfg.JobsURL),
		},
		Build: build(cfg),
	}), "identityx exited with error")
}

func build(cfg config.Config) backend.BuildFunc {
	return func(ctx context.Context, d backend.Deps, r chi.Router) error {
		repos := repos.New(sqlc.New(d.DB))

		keys := keys.NewManager(repos.CryptoKeys, repos.Projects, cfg.KeyPolicy())
		err := keys.EnsureAll(ctx) // every scope has keys before traffic
		if err != nil {
			return fmt.Errorf("ensure crypto keys: %w", err)
		}

		tokens := tokens.NewManager(repos, keys, cfg.TokenPolicy())
		actionTokens := tokens.NewActionTokenManager(repos.ActionTokens, cfg.ActionTokenPolicy())
		setupState := setup.NewState(repos.Actors) // was the global setup.UseProbe

		d.Jobs.Serve(jobs.Registry(jobs.Deps{Repos: repos, ActionTokens: actionTokens, Keys: keys, Email: d.Email}),
			jobs.Periodic(cfg.RotateKeysJobDuration)...)

		ops := services.New(services.Deps{
			Repos: repos, Tx: d.Tx, Jobs: d.Jobs, Keys: keys,
			Tokens: tokens, ActionTokens: actionTokens, Setup: setupState,
			HmacSecret: cfg.HmacSecret, AppURL: cfg.AppURL,
		})

		chains := d.Chains(authPrimitives(ops, tokens))
		mountStrict(r, handlers.NewServer(ops), chains)
		return nil
	}
}
```

Univents keeps what only it uses in `Build`:

```go
func main() {
	cfg := config.Load()
	errx.Exit(backend.Run(backend.App{
		Name:   "univents",
		Spec:   spec.OpenAPISpec,
		Server: cfg.Server,
		Modules: []backend.Module{
			postgres.Module(cfg.Postgres, constraintMessages()),
			identityx.Module(cfg.IdentityX, identityx.RequireVerifiedEmail(cfg.RequireVerifiedEmail)),
			email.Module(cfg.SMTP),
			jobs.Module(cfg.JobsURL),
		},
		Build: build(cfg),
	}), "univents exited with error")
}

func build(cfg config.Config) backend.BuildFunc {
	return func(ctx context.Context, d backend.Deps, r chi.Router) error {
		storage, err := objectstorage.New(ctx, cfg.ObjectStorage)
		if err != nil {
			return err
		}
		pay := payssage.New(cfg.Payssage)
		_, err = pay.GetWallet(ctx, cfg.PayssageWalletID) // fail fast
		if err != nil {
			return fmt.Errorf("payssage platform wallet check failed: %w", err)
		}
		notifier := database.NewNotifier(cfg.Postgres.DSN())

		repos := repos.New(sqlc.New(d.DB))

		d.Jobs.Serve(jobs.Registry(jobs.Deps{Repos: repos, Email: d.Email, Notifier: notifier, Tx: d.Tx}))

		ops := services.New(services.Deps{
			Repos: repos, Tx: d.Tx, Jobs: d.Jobs, IDX: d.IDX, Email: d.Email,
			Storage: storage, Payssage: pay, WalletID: cfg.PayssageWalletID,
			Notifier: notifier, HmacSecret: cfg.HmacSecret, WebhookSecret: cfg.PayssageWebhookSecret,
		})

		h := handlers.NewServer(ops)
		mountStrict(r, h, d.Chains(d.IDX.Auth))

		// Raw routes: outside the spec on purpose.
		r.Get("/editions/{edition_id}/store/stream", h.ServeStoreStream)
		r.Handle("/ws", http.HandlerFunc(h.ServeWS))
		return nil
	}
}
```

Univents' boot used to span `app.go`, `wire.go`, `router.go`, `auth.go` and `clients.go`, about 450 lines. Here it's `main` plus `build`, with no hand-written shutdown.

## Rollout

1. Build the kit next to `httpserver.Boot` without changing it.
2. Move the IdentityX auth primitives into the kit first. It's the largest copy, and the one that already caused a production bug.
3. Convert Informd first, since it has the smallest boot and no jobs, and compare the boot code before and after.
4. Convert Payssage, Univents and IdentityX, one pull request each. IdentityX's moves the setup guard and the `x-scope` checks into its services.
5. Delete the old `Boot` path and each backend's router setup.

## Consequences

- A backend's boot is `main` plus `Build`. Shared behavior is fixed in one place, so a fix like the IdentityX URL lands once for all four.
- Tests build a `Deps` by hand, with a test database and fakes, and call `Build`, instead of rebuilding routers in per-backend helpers.
- Infrastructure only one backend uses is opened in `Build`. It becomes a module when a second backend needs it.
- `Deps` grows a field per module. If it outgrows plain fields, we'll revisit, but not before.
