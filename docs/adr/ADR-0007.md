# ADR-0007 — The deploy gate is the only CI; main is latest-unstable

- **Status:** accepted
- **Date:** 2026-09-17
- **Scope:** `../../.github`, `../../.github`, `.husky/*`, `TrieOH/deploy` (separate repo, the ledger)

## Context

CI on every PR/merge to main (Dagger-based compile/test/lint/trivy) was hell for dev
velocity: a 2-person team pushing constantly had to pass a 5–7 minute pipeline on every
merge just to land code that was hours away from production. The checks were costing the
most exactly where the loop was tightest.

At the same time the asymmetry was backwards: `publish.yml` shipped tagged releases
blind — the only thing protecting main was the PR CI, and the only thing protecting prod
was nothing. A broken commit on main costs this team minutes (revert); a broken deploy is
client-facing. All checks lived where the cost was lowest, and deploys had no gate at all.

So the rework kills merge-blocking CI entirely and moves all checks to where the cost
actually is: the deploy. The priority is development and iteration speed, with safety
kept where it really matters — the production deploy.

## Decision

All automated quality checks moved to the deploy lane; main runs **zero CI**.

- **Three lanes, one repo.** Pushes/merges to `main` trigger nothing — main is
  *latest-unstable*, never prod. The quality layer for main is local git hooks
  (`.husky/`: commit-msg scope validation against a layout-discovered scope tree,
  pre-commit gitleaks diff scan + per-member checks, pre-push branch-naming). Release
  tags (`<artifact>/v<semver>`) trigger `deploy.yml`, the single workflow holding the
  full gate (ordered R-chain: compile → unit → lint → front → trivy → integration) plus
  all publish/deploy tails. `-hotfix.N` tags run compile + unit only (≤2 min to prod) —
  a reduced gate, not a bypass.
- **One deploy file.** `deploy.yml` replaced `ci.yml`, `frontend-lint-tsc.yml`,
  `trivy-scan.yml`, `publish.yml`, `publish-ts-sdks.yml`, and `deploy-front.yml`. All
  deploy logic lives in exactly one place; the tag prefix routes to the right tail.
- **No Dagger.** Native runner steps + cached composite actions
  (`../../.github`) instead: no engine spin-up, no per-step container
  overhead, direct runner caches. Speed and simplicity beat hermeticity for a 2-person
  team.
- **Digest-pinned ledger.** Build once, publish an immutable artifact, capture its
  digest (backend: image digest; frontend: Cloudflare Worker Version ID; SDKs: npm
  version). The pipeline writes `TrieOH/deploy`'s compose.yml (digests pinned, human
  tags in comments) and the server only executes (`compose pull && up -d --no-deps`).
  `:latest` left the deployment contract; humans keep read access and rollback.
- **No nightly/scheduled scanning.** The per-commit gitleaks diff scan in pre-commit is
  the between-deploys scanning mechanism; full trivy stays deploy-lane only.

## Consequences

- A broken build on main can sit unnoticed — accepted by design; checks re-run at tag
  time, so a deploy can't ship broken code. Branch protection on main is unchanged
  (admins push directly; it exists for consultants/juniors whose PRs run no CI — review
  is their gate).
- Hotfix tags deploy with no scanning at all — accepted risk, narrowed by the per-commit
  secret scan; the residual hole is `--no-verify` commits. Rotation runbook is the
  response, and the next normal release re-covers the skipped checks.
- Deploy frequency is low (client releases), so the 3–5 min warm pipeline at tag time is
  acceptable; correctness wins ties there.
- Anyone used to "CI on PR" will read the empty push trigger as a mistake. It is
  deliberate: the gate is the tag, not the merge. Don't "fix" it by re-adding CI to
  main.
- This shape is what makes the planned migration to ephemeral CI droplets viable
  (Forgejo runners on ephemeral, per-run droplets — decided in the staging/droplets
  plan). CI now runs only at tag time — infrequent, bursty, gate-sized — so paying a
  droplet spin-up per run is acceptable; paying it on every push to main would not be.
  A push-triggered CI would have permanently locked us into a permanent runner.
- Staging/E2E and the runner migration are decided in their own plan; the
  release-lock window there spans R-chain → E2E green → prod ledger commit.
