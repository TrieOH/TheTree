## Why

CI ran on every pull request and every merge to main: compile, test, lint and trivy, in Dagger, 5 to 7 minutes each time. For two people pushing all day, that wait landed exactly where we need speed most, on code that was hours away from production.

The protection was also in the wrong place. Releases shipped from `publish.yml` with no checks at all. A broken commit on main costs us a few minutes to revert. A broken deploy reaches clients. All the checks sat where breakage was cheap, and none sat where it was expensive.

So we moved every check to the deploy. Speed while developing comes first, and the safety stays on the production deploy, where it matters.

## Decision

main runs no CI. Every automated check runs on release.

- **main is latest, maybe broken.** Pushing or merging to `main` triggers nothing and never reaches production. Local git hooks in `.husky/` cover main: the commit-msg hook checks the commit scope, pre-commit runs a gitleaks scan of the diff and per-package checks, and pre-push checks the branch name.
- **A release tag runs the gate.** A tag `<artifact>/v<semver>` triggers `deploy.yml`, which runs compile, unit tests, lint, front checks, trivy and integration tests in that order, then publishes and deploys. A `-hotfix.N` tag runs only compile and unit tests, to reach production in under 2 minutes. That's a smaller gate, not a skip.
- **One entry point.** `deploy.yml` replaced `ci.yml`, `frontend-lint-tsc.yml`, `trivy-scan.yml`, `publish.yml`, `publish-ts-sdks.yml` and `deploy-front.yml`. It routes each tag by its pattern to one reusable workflow per kind of artifact: `_service.yml`, `_front.yml`, `_sdk.yml` and `_pages.yml`. Each one parses the tag first and is built from single-job composite actions in `.github/actions/<stack>/`. Only the publish step holds the per-artifact release lock, and a tag that a newer tag has replaced skips its deploy.
- **SDKs are checked, not published.** The SDK workflow is only the gate. We publish to npm by hand, because npm requires staged publishing for these packages.
- **No Dagger.** Plain runner steps and cached composite actions instead: no engine to start, no container per step, and the runner's own caches. For two people, speed and simplicity beat hermetic builds.
- **Deploys are pinned to what was built.** We build once, publish an immutable artifact and deploy it by its ID. Everything deploys to Cloudflare. A backend's binary is built once, by the checks that tested it, and put in an image (`api/Dockerfile.release`) that goes to GHCR by digest and to Cloudflare's registry from the same build, then ships as a Worker plus Container. A front ships a Worker version. The IDs are in each run's `release.json`. A report job sends every run's result, step timings and metrics to the dev portal's D1. `:latest` is never what we deploy.
- **No scheduled scans.** Between deploys, the gitleaks scan in pre-commit is the only scanning. The full trivy scan runs only on deploy.

## Consequences

- A broken build can sit on main unnoticed. That's by design: the checks run again at tag time, so broken code can't deploy. Branch protection on main is unchanged. Admins push directly, and it's there for outside contributors, whose pull requests run no CI. Review is their gate.
- Hotfix tags deploy with no scanning. The per-commit secret scan narrows the risk. The remaining hole is commits made with `--no-verify`. If a secret leaks, we follow the rotation runbook, and the next normal release runs the skipped checks.
- We release rarely, so 3 to 5 minutes at tag time is fine. Correctness wins there.
- If you're used to CI on every pull request, the empty push trigger looks like a mistake. It isn't: the gate is the tag, not the merge. Don't add CI back to main.
- Running CI only at tag time, rarely and in bursts, is what would let us move to short-lived runners that start per run. Paying that startup on every push to main would not be worth it.

## Changes

- **2026-11-05:** `deploy.yml` became a router to one reusable workflow per artifact type. The compose deploy ledger (the separate `TrieOH/deploy` repo) is gone: everything deploys to Cloudflare, and run data goes to the dev portal.
