## Why

ADR-0014 made boot readable: `main` plus `Build`. The code `Build` wires was still hard to follow, for the same reasons boot had been.

- **A feature was spread across the tree.** Informd's `steps` lived in `models/`, `ports/`, `internal/repos/steps`, `internal/services/steps`, `internal/handlers/steps`, and three files (`repos.go`, `services.go`, `handlers/server.go`) that held only aliases. Adding a feature touched all of them.
- **Long constructors.** ADR-0014 asked for struct arguments, but the services kept positional ones. Univents' `checkouts.NewOperations` took 20 arguments on one line.
- **The same lines in every operation.** Each operation and repo method opened its own span, about 570 `telemetry.StartSpan` calls, even though the pgx tracer already records every query. Each guarded operation looked up the caller and then passed its ID to the access check (`RequireIdentity`, then `CheckForm(ctx, ident.Sub.ID, …)`), about 170 times.

## Decision

- **A feature is one folder and one package.** Instead of `layer/feature`, it's `feature/` with everything inside:

  ```
  internal/features/steps/
    repo.go        // the repo: Repo, NewRepo
    handlers.go    // every handler: Handlers, NewHandlers
    operations.go  // Deps, Operations, New and every operation
    spec.yml       // the feature's part of the spec (ADR-0021)
  ```

  Repo methods end with `database.One` or `database.Many`. A feature with only a repo, like Informd's `answers`, has only `repo.go`. Webhook capture middleware keeps its own `middleware.go`. When `operations.go` gets too big, it's split by flow, as in Univents' `checkouts`. A feature's own subpackages, like `jobs`, sit inside its folder (`features/checkouts/jobs`).
- **Shared code that isn't a feature lives outside `features/`.** Univents' NOTIFY contract is `internal/notify`, and Payssage's MercadoPago adapter sits with its models in `internal/providers`. `models/` and `ports/` stay shared: domain types and repo interfaces cross features, and keeping them in leaf packages stops features from importing each other. A feature that needs another's operations declares a small interface for them, like Univents' `checkouts` taking `Badges`. IdentityX's `authn` and `oauth_providers` still take `tos`'s concrete operations.
- **`Build` imports one package per feature.** The alias files are gone. `Build` lists the repos, then each feature's operations, then the server that embeds every feature's handlers.
- **Operations take a `Deps` struct** with exported fields. `Operations` embeds it, so operations read `o.Steps`, `o.Authz`, `o.Tx`. A test fills only the fields it uses. State the operations work out for themselves, like a retry budget or the WebSocket hub, stays unexported on `Operations` and is set in `New`. IdentityX's `errx.MustProvide` wrappers are removed. They skipped unexported fields, so they never checked anything, and on exported fields they would start rejecting the nil dependencies tests pass.

  ```go
  steps.New(steps.Deps{Forms: formsRepo, Steps: stepsRepo, Namespaces: namespacesRepo, Authz: az})
  ```

- **Access checks find the caller and return it.** `authz.Form(ctx, formID, minRole) (*idx.Identity, error)` reads the identity the auth middleware stored and checks the role, as IdentityX's `internal/authz` already did. Operations that need the caller keep it, and the rest ignore it. Operations that only need someone signed in, like creating something they'll own, call `idx.RequireIdentity` directly. An operation that compares the caller with its input before the access check (you can't add yourself) still looks the caller up first, so a 400 still comes before a 403. When the subject isn't the caller, like staff admitting an attendee to a staff-only program, or an operation is handed its actor, the check takes the actor as an argument (Univents' `EventFor`).
- **The harness opens one span per operation.** `httpserver.StrictStack`, used by each backend's generated `openapi.Mount`, adds `TraceMiddleware` as the outermost strict middleware. It opens a span named after the operation ID and records any returned error on it. Repos and services open no spans of their own: the pgx tracer covers queries, and the job registry already spans each job. A manual span stays only where one step inside an operation is worth seeing alone, like a provider call.

## Consequences

- One folder holds a feature. Adding one is a folder, a line per part in `Build`, and the spec.
- Span names change from `StepService.Create` and `StepRepo.Create` to the operation ID (`CreateStep`). Dashboards using the old names need updating.
- `Build` grows a line per repo and a `Deps` literal per feature. It's long, but it's the whole graph in one place, in order.
- The server embeds every feature's `Handlers`, and Go needs a distinct field name for each. `tools/strictmount` generates those aliases in `internal/app/server.gen.go`, one per feature folder that declares `Handlers`, named after the folder (`api_keys` becomes `apiKeysHandlers`).
- Database tests that seed data through several features use `internal/testrepos` (Univents, IdentityX): every repo over one query handle, imported only by tests. A test inside a feature package can't import `testrepos`, because `testrepos` imports the feature, so database tests live in `<feature>_test`.
- Guarded operations now load their resource before the check rejects a missing caller. Production never reaches an operation without one, since the auth chains run first. Unit tests that send no identity stub the load.

## Changes

- **2026-10-29:** a feature's repo became one `repo.go`, and its handlers one `handlers.go`. Both moved from subpackages into the feature package (`NewRepo`, `NewHandlers`).
- **2026-11-19:** the operations moved into the feature package too, in one `operations.go`, and the `<feature>.go` alias file was removed.
- **2026-11-21:** the embedded handler aliases are generated into `internal/app/server.gen.go`.
