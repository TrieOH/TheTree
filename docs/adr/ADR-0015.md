# ADR-0015 — Features are folders, operations take a Deps struct

- **Status:** accepted; `repo/` amended 2026-10-29 — a feature's repo is one
  `repo.go`, its methods finished by `database.One`/`database.Many`
- **Date:** 2026-10-24
- **Scope:** `lib/go/httpserver`, `api/{identityx,informd,payssage,univents}/internal`

## Context

ADR-0014 made a Backend's boot readable: `main` plus `Build`. The code
`Build` wires is still hard to follow, for the same reasons boot was:

- **A feature is spread across the tree.** Informd's `steps` lives in
  `models/`, `ports/`, `internal/repos/steps`, `internal/services/steps`,
  `internal/handlers/steps` and three aggregator files (`repos.go`,
  `services.go`, `handlers/server.go`) that hold only type and constructor
  aliases. Adding a feature touches all of them.
- **Long positional constructors.** ADR-0014 asked for `Deps`-style
  structs; the services kept positional ones. Univents'
  `checkouts.NewOperations` takes 20 arguments, wired in one line.
- **The same lines in every operation.** Each operation and repo method
  opened its own span (about 570 `telemetry.StartSpan` calls), although the
  pgx tracer already records every query. Each guarded operation looked up
  the caller, then passed the caller's id to the access check
  (`RequireIdentity` then `CheckForm(ctx, ident.Sub.ID, …)`), about 170
  times.

## Decision

- **A feature is a folder, layers are its subfolders.** The axis flips
  from `layer/feature` to `feature/layer`; files are moved, not merged:

  ```
  internal/features/steps/
    steps.go     // the feature's wiring surface
    repo/        // repo.go: the whole repo (amended, see Status)
    service/     // operations.go (Deps, Operations, New) + one file per operation
    handlers/    // handlers.go + one file per operation
  ```

  A service's sub-packages (e.g. `jobs`) sit next to the layers
  (`features/checkouts/jobs`). A feature with only a repo (Informd's
  `answers`) has only `repo/`. Shared code that is not a feature leaves the
  tree: Univents' NOTIFY contract is `internal/notify`, Payssage's
  MercadoPago adapter sits with its models in `internal/providers`.
  `models/` and `ports/` stay shared: domain types and repo interfaces
  cross features, and keeping them in leaf packages is what lets features
  avoid importing each other. A feature that needs another feature's
  operations takes a small interface it declares (Univents' `checkouts`
  takes `Badges`); IdentityX's `authn` and `oauth_providers` still take
  `tos`'s concrete operations.
- **The feature file is the only aggregator.** `steps.go` re-exports the
  layer types (`Repo`, `Deps`, `Operations`, `Handlers`) and constructors
  (`NewRepo`, `New`, `NewHandlers`), so `Build` imports one package per
  feature. The per-layer aggregator files are gone; `Build` lists the
  repos, then each feature's operations, then the server that embeds every
  feature's handlers.
- **Operations take a Deps struct.** `service.Deps` lists what the
  operations need, with exported fields; `Operations` embeds it, so the
  operations read `o.Steps`, `o.Authz`, `o.Tx`. A test fills only the
  fields it exercises. State the operations derive (a retry budget, the WS
  hub) stays unexported on `Operations` and is set in `New`. IdentityX's
  `errx.MustProvide` wrappers go: they skip unexported fields, so they
  never checked anything, and on exported `Deps` they would start
  rejecting the nil dependencies tests pass.

  ```go
  steps.New(steps.Deps{Forms: formsRepo, Steps: stepsRepo, Namespaces: namespacesRepo, Authz: az})
  ```

- **Access checks resolve the caller and return it.** `authz.Form(ctx,
  formID, minRole) (*idx.Identity, error)` reads the identity the auth
  middleware wrote and checks the role, as IdentityX's `internal/authz`
  already does. Operations that need the caller keep the returned
  identity; the rest discard it. Operations that only need a signed-in
  caller (creating something they will own) call `idx.RequireIdentity`
  directly. An operation that compares the caller with its input before the
  access check (no adding yourself) still looks the caller up first, so the
  400-before-403 order does not change. Where the subject is not the caller
  (staff admitting an attendee to a staff-only program) or an operation is
  handed its actor, the check takes the actor explicitly (Univents'
  `EventFor`).
- **One span per operation, from the harness.** `httpserver.MountStrict`
  adds `TraceMiddleware` as the outermost strict middleware: a span named
  after the operationID, with a returned error recorded on it. Repos and
  services open no spans of their own; the pgx tracer covers queries and
  the job registry already spans each job. A manual span stays where a step
  inside an operation is worth seeing on its own (a provider call).

## Consequences

- One folder holds a feature; adding one is a folder, a line per layer in
  `Build`, and the spec.
- Span names change from `StepService.Create` / `StepRepo.Create` to the
  operationId (`CreateStep`); dashboards keyed on the old names need
  updating.
- `Build` grows a line per repo and a `Deps` literal per feature. It is
  long, but it is the whole graph in one place and in order.
- The embedded-handler aliases in the server stay: Go needs a distinct
  field name per embedded `Handlers`.
- DB tests that seed through several features use `internal/testrepos`
  (Univents, IdentityX): every repo over one query handle, imported by
  tests only.
- Guarded operations now load their resource before the check rejects a
  missing caller. Production never reaches an operation without one (the
  spec-derived chains authenticate first); unit tests that send no
  identity stub the load.
