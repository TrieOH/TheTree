# ADR-0005 — Scope is a chain concern when derived from the spec's `x-scope`

- **Status:** accepted
- **Date:** 2026-08-15
- **Scope:** `lib/go/authz`, `api/identityx/internal/{app,authz,handlers}`, `api/identityx/api-spec.yml`

## Context

ADR-0003 replaced the hand-maintained `clientOnlyOps` route list with per-handler
enforcement of platform-vs-project scope: `handlers.RequireClientOnly` became the
first statement of every platform-only handler (~26 of them). That killed the list,
but left two failure modes:

1. **Per-site enforcement.** A new handler that forgets its first line silently
   widens the surface. The regression net (`clientOnlyMethods` in
   `internal/handlers/handlers_test.go`) was itself a hand list duplicating the
   spec — the same smell ADR-0003 removed, one level down.
2. **Two modules answer "who may touch this".** The scope half (client kind) lived
   at the HTTP binding; the role half (`authz.Service.CheckProject`/`CheckOrg`/
   `CheckPlatform`) lived at the operations seam. Scope policy was untestable
   without HTTP, and `RequireProjectClientOnly` sat in `models` with no caller.

The spec already is the single source of truth for *authentication* (security
blocks → derived chains, fail-fast at boot). Scope is the same kind of fact about
an operation: a caller-class predicate, not a per-resource rule. It belongs to the
same derivation.

## Decision

Scope is a chain concern, derived from the spec, exactly like the auth schemes:

- Operations declare `x-scope: <name>` (per-operation only; no document-level
  default; absent = no scope restriction).
- `lib/authz` parses `x-scope` in `SpecOperations`; `Primitives` gains
  `Scopes map[string]ScopeChecker`, where `ScopeChecker = func(ctx) error` is a
  plain predicate reading the identity the auth middleware wrote. A nil registry
  disables scope support — backends whose specs declare no `x-scope` are
  untouched.
- `NewResolver` validates every declared scope against the registry and fails
  boot on a miss; an `x-scope` on an operation with `security: []` is also a boot
  error (a scope implies authentication). The scope middleware runs after the
  authn primitive, so the chain is `[setupGuard?, authn, scope]`.
- identityx registers its checkers in the Access-check module:
  `authz.Service.ScopeCheckers()` returns `{"platform-only": ...}` (the old
  `RequireClientOnly` logic, moved from `models`). `models.RequireClientOnly` and
  `models.RequireProjectClientOnly` are deleted — the latter never earned a
  caller. Adding a scope is one spec line plus one checker entry.
- `internal/handlers` lose their guard first-lines and become pure binding. The
  `clientOnlyMethods` hand list is deleted; the parity test
  (`TestAuthMatrixMatchesSpec`) derives the expected chain — including the scope
  middleware — from the spec, so the resolver cannot drift from it.
- `getPlatformProfile` was declared `security: []` ("Public read") in the spec but
  guarded in the handler, so it 401'd every caller; it is now `security:
  bearerAuth` (JWT-only) with `x-scope: platform-only`, matching its enforcement
  and its private use by the IdentityX UI.

## Consequences

- A dropped `x-scope` annotation is a spec change, visible in review, and the
  parity net pins the surface; enforcement can no longer be forgotten per handler.
- Scope checkers are predicates — testable directly without HTTP, beside the role
  checks in the Access-check module.
- The mechanism is generic in `lib/authz`: any backend can declare scopes and
  register custom checkers without touching the resolver.
- Supersedes ADR-0003's "platform-vs-project scope is not a chain concern" note;
  ADR-0003's other decisions (spec-derived chains, fail-fast, no hand lists)
  stand.
