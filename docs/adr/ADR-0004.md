# ADR-0004 — Authorization injected through the operations seam

- **Status:** accepted
- **Date:** 2026-08-01
- **Scope:** `api/{informd,payssage,univents}/internal/authz`, `api/{informd,payssage,univents}/internal/services`, `api/univents/internal/services/badges`

## Context

Three backends (informd, payssage, univents) exposed authorization through a
package-level service locator: `var Service *service` in `internal/authz`,
assigned at boot in `wire.go` and **reassigned directly inside unit tests**.
Consequences:

- Construction order matters and is implicit; there is no per-request or
  per-test instance.
- Policy has no single home, so it degrades feature-by-feature: the `badges`
  feature shipped with no identity check and no role check at all, while
  every sibling feature opened with `idx.RequireIdentity` + `CheckEvent`.
- identityx was already the counter-example: it constructor-injects
  `*authz.Service` through `services.NewOperations` and has no global.

## Decision

- Export the authz type (`service` → `Service`) and delete `var Service` in
  all three backends.
- Every feature operations struct gains an `authz *authz.Service` field,
  constructor-injected through `services.NewOperations`, exactly as
  identityx does. `wire.go` constructs the service once from the repos and
  passes it down; tests construct a fresh instance per test through the same
  seam (the authz constructors already accept ports — `ports.EventRepo`,
  `ports.FormsRepo`, `ports.OrganizationRepo` — so existing test fakes work
  unchanged).
- The `badges` feature gains the missing guard: `RequireIdentity` +
  `CheckEvent(..., EventMemberRoleAdmin)` on its write operations, mirroring
  the sibling `certifications` feature.

## Consequences

- `authz.Service` no longer exists anywhere; tests stop mutating process
  state. The operations interface names its authorization dependency.
- Features that take `authz` by construction can't silently forget it the
  way `badges` did.
- The per-feature role policy (which operation requires which role) remains
  inline per operation — centralizing it into a policy table is a separate
  deepening, tracked for later.

## Rejected alternatives

- **Context-based authorization** — identity already travels via context;
  adding authorization there would hide the dependency from the interface
  and reintroduce the same test-mutation problem.
- **Per-feature authz instances** — no feature needs a different policy
  instance today; one instance per backend is the demonstrated need
  (one adapter per seam).
