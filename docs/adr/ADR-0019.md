## Why

ADR-0017 made a success the plain payload, but errors stayed our own `{code, message, fields}` object. Its `code` was the status in another form, and nothing read it except to check it was a string. ADR-0016 put every error-to-status decision in one table per backend, but the table named statuses and codes, not documented problems, and the specs described every failure with one generic `Error` schema. A client couldn't tell from the spec which failures an operation can return, and a backend could map an error to a status no spec mentioned.

This replaces ADR-0017's error object and ADR-0016's table, and closes backend wishlist #14.

## Decision

- **Every error is an RFC 9457 problem,** sent as `application/problem+json` through `problematic` (`fp.Write`). It always has `type`, `status`, `title`, `detail` and `instance`, plus the problem's own fields. `errors: [{field, message}]` is added when the failure is about request fields (`fielderr`). There's no `code`.
  - `title` is the declared problem's title. `detail` is the matched error's message. A 500 reads `Internal Server Error`, and its cause goes to logs and the span.
  - `instance` is the request path, set by the writer.
  - `type` is `{API_URL}/problems/{slug}`. Every backend requires the `API_URL` env var (`config.Server`), so `type` differs per environment and points at the API that answered. `GET /problems/{slug}` serves the problem's docs.
- **Problems are declared in YAML, next to the spec, and nowhere else.** `api/problems.yml` holds the shared ones (not found, validation, batch, the auth 401s, insufficient role, rate limited, internal). Each backend's `api/<svc>/problems.yml` holds its own. A problem is a schema with an `x-problem` block (`slug`, `status`, `title`, `description`) and only its own extra fields. Both files are found by convention.
- **`tools/go/problemgen` bundles and generates** (`just gen`). The bundle, `api/<svc>/api-spec.gen.yml` (gitignored), is the one spec that oapi-codegen, orval, the auth resolver and `/docs/openapi.yml` read. `api/<svc>/internal/problems` (gitignored) gets one constructor per problem, with its slug, status and title fixed and its extra fields as typed arguments. Mapping to a problem that isn't declared doesn't compile.
- **The mapper is a switch.** Each backend's `Problem` func (in `internal/app/errmap`, apart from `internal/app` so feature tests can import it) is a plain `switch` of `errors.Is` and `errors.As` cases returning generated constructors. `problems.Mapper(errmap.Problem)` tries it first, then the generated shared cases (`database.NotFoundError` and plain `ErrNotFound`, `BatchError`, `authz.ErrInsufficientRole`, `validator.Error`, `idx.ErrNoIdentity`, and the harness's auth and binding sentinels). It's one line in each backend, `backend.App.Errors`.
- **Database errors reach clients only as named errors.** A registered constraint needs a case in the switch. An unregistered one, or a bare constraint class, is a plain 500. To answer it, register the constraint.
- **One writer.** `httpserver.WriteError` maps through the installed mapper for strict handlers, param binding and body decoding, auth, recover, rate limit and scope checks. Batch items go through the same switch (`httpserver.ProblemType`).
- **Each operation lists its problems.** `x-problems` on an operation names slugs or statuses. A status means every problem the backend declares with that status. The bundle turns them into error responses. The writer checks each answered slug against its operation's list: under `go test` and `DEBUG_MODE` it panics, and in production it logs a warning and sets the span attribute `problem.unlisted`. The response itself never changes. `just e2e-down` prints the unlisted ones from the logs.
- **Clients read the problem.** The Go SDKs' `APIError` is `{StatusCode, Type, Title, Message}`, with `Message` taken from `detail`. The TS SDKs' and `@trieoh/api-client`'s `toFailure` take the message from `detail`, or `title` if there's none. `error_id` isn't filled any more.

## Consequences

- A new error a client can see is a line in `errs`, a problem in `problems.yml`, a case in the switch, and its slug or status on each operation that can return it. Forget the case and it's a 500. Forget the operation and any test that hits it panics.
- The spec tells clients every problem an operation can return, and each problem type is documented at its own URL.
- Unregistered constraints answer 500 instead of a 409 or 400 by class.
- `APIError.Code` is gone from the Go SDKs. The TS SDKs were bumped (`@trieoh/identityx-sdk-ts@0.16.4`, `@trieoh/identityx-access-sdk-ts@0.1.11`).
- **Still open:** operations list problems by status for now. Working out each operation's own slugs from the errors its handler can return comes later. `sdk/ts/payssage` still reads envoy-fetch's defaults and will be deleted or rewritten (ADR-0017).

## Changes

- ADR-0021 moved each feature's problems into its `spec.yml`, and ADR-0022 generates most sentinels and mapper cases from the problem declarations.
