# ADR-0019 — Errors are RFC 9457 problems, declared in the spec

- **Status:** accepted
- **Date:** 2026-10-29
- **Scope:** `MintzyG/problematic`, `tools/go/problemgen`, `lib/go/{httpserver,backend,config}`, `api/{identityx,informd,payssage,univents}` (specs, `problems.yml`, mappers), `sdk/go/{IdentityX,Payssage}`, `sdk/ts/{identityx,identityx-access}`, `front/identityx`
- **Supersedes:** ADR-0017's error object (`{code, message, fields}`) and ADR-0016's error map table. Closes backend wishlist #14.

## Context

ADR-0017 made success the plain payload but left errors a bespoke
`{code, message, fields}` object. Its `code` was the status in another
form, and nothing read it beyond checking it was a string. ADR-0016 put
every error → status decision in one table per Backend, but the table
named statuses and codes, not documented problems, and the specs
described every failure with one generic `Error` schema. A client could
not tell from the spec which failures an operation can answer, and a
Backend could map an error to a status no spec mentioned.

## Decision

- **Every error the process writes is an RFC 9457 problem**, served as
  `application/problem+json` through `problematic` (`fp.Write`). Members:
  `type`, `status`, `title`, `detail`, `instance`, always present, plus
  the problem's own extensions. `errors: [{field, message}]` is added
  when the failure names request fields (`fielderr`). No `code`.
  - `title` is the declared problem's; `detail` is the matched error's
    message; a 500 reads `Internal Server Error` and its cause goes to
    logs and the span.
  - `instance` is the request path, set by the writer.
  - `type` is `{API_URL}/problems/{slug}`. `API_URL` is a required env
    var on every Backend (`config.Server`), so `type` differs per
    environment and dereferences against the API that answered.
    `GET /problems/{slug}` serves the problem's documentation.
- **Problems are declared in the spec, and only there.** `api/problems.yml`
  holds the shared ones (not found, validation, batch, the auth 401s,
  insufficient role, rate limited, internal) and each Backend's
  `api/<svc>/problems.yml` its own: a schema with an `x-problem` block
  (`slug`, `status`, `title`, `description`) and only its extension
  members. Both load by convention, next to the spec.
- **`tools/go/problemgen` bundles and generates** (`just gen`): the
  bundle `api/<svc>/api-spec.gen.yml` (gitignored) is the one spec that
  oapi-codegen, orval, the authz resolver and `/docs/openapi.yml` read;
  `api/<svc>/internal/problems` (gitignored) gets one constructor per
  problem, its slug, status and title fixed, its extensions typed
  parameters. Mapping to an undeclared problem does not compile.
- **The mapper is a switch.** Each Backend's `Problem` func
  (`internal/app/problems.go`, univents `internal/app/errmap`) is a
  tagless `switch` of `errors.Is` / `errors.As` cases returning
  generated constructors. `problems.Mapper(app.Problem)` tries it, then
  the generated shared cases (`database.NotFoundError` and the bare
  `ErrNotFound`, `BatchError`, `authz.ErrInsufficientRole`,
  `validator.Error`, `idx.ErrNoIdentity`, the harness's auth and
  binding sentinels); it is the Backend's one wiring line
  (`backend.App.Errors`).
- **Database errors reach clients only as named errors.** A registered
  constraint needs a case in the switch; an unregistered one, or a bare
  constraint class, is a generic 500. Register the constraint to answer
  it.
- **One writer.** `httpserver.WriteError` maps through the installed
  mapper for strict handlers, param binding and body decode, auth,
  recover, rate limit and scope checks. Batch items resolve through the
  same switch (`httpserver.ProblemType`).
- **Each operation lists its problems.** `x-problems` on an operation
  names slugs or statuses (a status means every problem the Backend
  declares with it). The bundle rewrites them into error responses. The
  writer checks an answered slug against its operation's list: panic
  under `go test` and `DEBUG_MODE`, a warning plus span attribute
  `problem.unlisted` in prod; the response never changes. `just e2e-down`
  prints the unlisted ones from the logs.
- **Clients read the problem.** The Go SDKs' `APIError` is
  `{StatusCode, Type, Title, Message}` with `Message` the `detail`. The TS
  SDKs' and `@trieoh/api-client`'s `toFailure` take the message from
  `detail`, else `title`; `error_id` is no longer filled.

## Consequences

- A new user-facing error is a line in `errs`, a problem in
  `problems.yml`, a case in the switch, and its slug or status in each
  operation that can answer it. Forgetting the case is a 500; forgetting
  the operation panics any test that answers it.
- The spec tells clients every problem an operation can answer, and the
  problem types are documented at their own URL.
- Unregistered constraints answer 500 instead of 409/400 by class.
- `APIError.Code` is gone from the Go SDKs; the TS SDKs bumped
  (`@trieoh/identityx-sdk-ts@0.16.4`,
  `@trieoh/identityx-access-sdk-ts@0.1.11`).
- **Open:** operations list problems by status for now. Deriving each
  operation's own slugs (from the errors its handler can return) is a
  later change. `sdk/ts/payssage` still reads envoy-fetch's defaults and
  is to be deleted or rewritten (ADR-0017).
