## Why

Every response was wrapped in the `fun.Response` envelope, `{code, message, data, error, timestamp, module}`. HTTP details sat inside the body: the status was repeated as `code`, a list was a bare array under `data` with no room for paging, and an empty answer was a 200 with an envelope and no `data`. Every client had to unwrap it: the orval mutator plus an orval input transformer, envoy-fetch's default mappers, the BFF, the Go SDKs and the e2e keywords.

ADR-0016 moved error decisions into one map per backend but kept the envelope, and said removing it would come later. The backends then dropped it one at a time (pull requests #52 to #56), with every client reading both shapes in between. This ADR records where that ended, now that nothing reads two shapes any more.

## Decision

- **A success is the payload itself,** with no `code`, `message`, `timestamp` or `module` around it.
- **A list is `{ "items": [ … ] }`,** never a bare array, so paging fields (TRI-20) can go next to `items` without another breaking change.
- **Nothing to return is `204 No Content`** with no body.
- **Every error is one flat object:** `{ "code": "VALIDATION_ERROR", "message": "…", "fields": [{ "field", "message" }] }`, with `fields` only when the failure is about request fields. `code` is a string from the `fun` error codes, and the HTTP status is only the status. Strict handlers, param binding, authz and the `fun` middlewares (auth 401, recover 500, rate limit 429) all write through the one writer in `lib/go/httpserver`. There's no switch to turn it off. It's the only format.
- **`/health` is plain too:** `{ "status": "ok", "service": "<name>" }`, written by the harness instead of `fun/handlers`. `/.well-known/jwks.json` was always plain.
- **Root `fun` no longer writes responses.** `SetupFUN` only installs the validator and the middlewares' error writer. `fun.SetConfig`, the 500 interceptor and the `AppErrorMapper` registration are gone. `fun.AppError` and the code constants stay as the writer's internal carrier.
- **TS clients read the response directly** with envoy-fetch's `toSuccess` and `toFailure` hooks (`@trieoh/api-client/wire`, with a copy in each published SDK's `wire.ts`), instead of rebuilding a fake envelope for envoy's defaults. They still fill envoy-fetch's `DefaultFetchResult`, which is the library's in-memory type, not what's on the wire. On a failure, its `code` is the HTTP status and `error_id` is the error's code. On a success, `code` always reads 200, since `toSuccess` never sees the status. Nothing reads it.

## Consequences

- The specs describe the payloads directly. Generated Go handlers return them, and orval needs no transformer.
- A client that gets an unexpected shape now fails loudly. Nothing checks "is this an envelope?" any more.
- The Go SDKs' `APIError.Code` is the error's string code (`NOT_FOUND`), not a number.
- **Next: RFC 9457.** Errors will become `application/problem+json` (backend wishlist #14). The TS readers in `lib/ts` and the e2e `Error Of` keyword already accept a problem (`detail` or `title`, `code`, `errors`), so that move is a writer swap in `lib/go/httpserver` plus the SDKs' `toFailure`.
- **Not done here:** the BFF's responses to the browser (`ServerProxyResult`: `{success, code, data, message, error_id}`) and envoy-fetch's envelope words (`FetchClientError.envelope`, `module`, `timestamp`) are unchanged. Replacing them needs a plain failure type across the published TS SDKs, which is a breaking release, and a new envoy-fetch release. `sdk/ts/payssage` still calls routes the spec no longer has. It will be deleted or rewritten, not migrated.

## Changes

- ADR-0019 replaced the flat error object with RFC 9457 problems.
