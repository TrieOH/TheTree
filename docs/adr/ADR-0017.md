# ADR-0017 — The wire is plain JSON; errors are one bare object

- **Status:** accepted
- **Date:** 2026-10-29
- **Scope:** `lib/go/{httpserver,backend}`, `api/{identityx,informd,payssage,univents}` (specs and handlers), `sdk/go/{IdentityX,Payssage}`, `lib/ts/{api-client,front-core}`, `sdk/ts/{identityx,identityx-access}`, the fronts, `e2e/`

## Context

Every response rode the `fun.Response` envelope
(`{code, message, data, error, timestamp, module}`). HTTP semantics sat
inside the body: the status was repeated as `code`, a list was a bare
array under `data` with nowhere to put paging, and an empty answer was a
200 carrying an envelope with no `data`. Every client had to unwrap it:
the orval mutator and an orval input transformer, envoy-fetch's default
mappers, the BFF, the Go SDKs, and the e2e keywords.

ADR-0016 moved error *decisions* into one map per Backend but kept the
envelope on the wire, and named removing it as a later change. The
Backends then moved off it one at a time (PRs #52 to #56), with every
client reading both shapes in between. This ADR records where that
landed, now that the two-shape readers are gone.

## Decision

- **Success is the payload itself.** No `code`, `message`, `timestamp`
  or `module` around it.
- **A list is `{ "items": [ … ] }`,** never a bare array, so paging
  fields (backend wishlist #13) can sit next to `items` without another
  break.
- **Nothing to return is `204 No Content`** with no body.
- **Every error the process writes is one bare object:**
  `{ "code": "VALIDATION_ERROR", "message": "…", "fields": [{ "field", "message" }] }`,
  `fields` only when the failure names request fields. `code` is a
  string from the `fun` error codes; the HTTP status is only the status.
  Strict handlers, param binding, authz and the `fun` middlewares (auth
  401, recover 500, rate limit 429) all write through
  `lib/httpserver`'s one writer. There is no switch: it is the only
  format.
- **`/health` is plain too:** `{ "status": "ok", "service": "<name>" }`,
  written by the harness, not `fun/handlers`. `/.well-known/jwks.json`
  was always bare.
- **Root `fun` no longer writes responses.** `SetupFUN` only installs
  the validator and the middlewares' error writer; `fun.SetConfig`, the
  500 interceptor and the `AppErrorMapper` registration are gone.
  `fun.AppError` and the code constants stay as the writer's internal
  carrier.
- **TS clients read the wire directly** with envoy-fetch's `toSuccess` /
  `toFailure` hooks (`@trieoh/api-client/wire`, and a copy in each
  published SDK's `wire.ts`), instead of rewriting each `Response` into a
  fake envelope for envoy's defaults. They still fill envoy-fetch's
  `DefaultFetchResult`. That is the client library's in-memory type, not
  the wire: on a failure `code` is the HTTP status and `error_id` the
  error's code. A success's `code` reads 200 whatever the status, since
  `toSuccess` never sees it. Nothing reads it.

## Consequences

- Specs describe the payloads directly. Generated Go handlers return
  them, and orval needs no transformer.
- A client failing on an unexpected shape now fails loudly instead of
  being papered over by a probe. No reader checks "is this an envelope?"
  any more.
- The Go SDKs' `APIError.Code` is the error's string code (`NOT_FOUND`),
  not a number.
- **Still to come: RFC 9457.** Errors become `application/problem+json`
  (backend wishlist #14). The TS readers in `lib/ts` and the e2e
  `Error Of` already accept a problem (`detail`/`title`, `code`,
  `errors`), so that move is a writer swap in `lib/httpserver`
  (ADR-0016) plus the SDKs' `toFailure`.
- **Not done here:** the BFF-to-browser responses (`ServerProxyResult`:
  `{success, code, data, message, error_id}`) and envoy-fetch's envelope
  vocabulary (`FetchClientError.envelope`, `module`, `timestamp`) are
  unchanged. Replacing them means a plain failure type across the
  published TS SDKs (a breaking release) and an envoy-fetch release.
  `sdk/ts/payssage` still targets routes the spec no longer has; it is to
  be deleted or rewritten, not migrated.
