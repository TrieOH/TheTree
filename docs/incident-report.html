Incident Report

trieoh host saturation during Forgejo Actions publish build

Date: 2026-08-26, 17:04–17:34 UTC (30 min)  ·  Severity: high (full host unresponsive, no data loss)  ·  Status: Resolved — natural recovery, build succeeded

Summary

A routine publish build (univents/v0.10.12, commit d9dec307, tag pushed 17:03 UTC) ran the dagger publish workflow inside forgejo-dind on the trieoh host (2 cores / 7.8 GiB / zero swap). The build was capped at the dind limit (then 1.5 CPU / 3 GiB) and succeeded — but for ~18 minutes it pinned the host at 100% CPU, starved Forgejo so badly the Actions runner could not report for 15 minutes, and made every service unresponsive. Recovery was natural: when the build finished (17:34), the box settled on its own.

Why it happened — in one sentence:

A CI job allocated 75% of the host's only 2 cores on a machine already running the full service stack, and the runner's aggressive 1-second reporting turned Forgejo's normal slowness into a retry storm that ballooned Forgejo to ~2 GB and ~90% CPU — a self-amplifying loop until the build finished.

Key numbers

  • CPU: 100% for ~18 minutes on a 2-core box (load 1-min peak 21.7)
  • RAM: actual anonymous memory peaked at 5.08 / 7.75 GiB (65.5%) — never exhausted, no OOM-killer events, no container crashed
  • Why it "looked" like 100% RAM: ~2.6 GiB of page cache on top; with no swap and 8.6 GB of disk writes in 30 min, the kernel constantly reclaimed cache → everything thrashed
  • Disk: 30.9 → 39.5 G during the build (+8.6 G of images/buildkit cache)
  • Forgejo leak: container creeps ~250 MB → 550+ MB per day (daily 05:00 restart resets it); was already at 564 MB before the build (12 h of creep)
  • Outcome: build succeeded, image pushed, zero data loss

Root cause — three layers

  1. Trigger: a normal publish build (univents v0.10.12). Not a runaway — just a build on a machine with no headroom.
  2. Co-tenancy: the whole stack (Forgejo + Postgres + Grafana + 3× Victoria + 4 apps + mox + ntfy + beszel ≈ 2.5–3 GiB baseline) shares a 2-core / 7.8 GiB / no-swap box with CI. dind's 1.5-core cap = 75% of all CPU.
  3. The amplifier — retry storm: runner report_interval: 1s with short client timeouts. When Forgejo slowed, the runner hammered it with timed-out retries → Forgejo ballooned to ~2 GB / ~90% CPU → slower → more timeouts. Forgejo (not the build) was the single biggest CPU consumer of the incident.

Evidence trail

  • beszel history (SQLite, 30-day retention): host + per-container minute-level CPU/RAM — the timeline above
  • Runner logs: task 1213 pickup 17:04:24; context deadline exceeded reporting to forgejo:3000 17:07–17:22
  • Kernel logs: no OOM-killer events in the window (nothing was ever killed)
  • docker inspect: dind limits confirmed applied (Compose v5.3.1 honors deploy.resources.limits)
  • dagger engine container exited 0 at 17:34 — build completed cleanly

Action items

AppliedRunner retry storm fix

forgejo/runner/config.yml: report_interval 1s → 5s, fetch_timeout 5s → 20s, fetch_interval 2s → 5s. Removes the feedback loop.

AppliedRight-size dind

forgejo/compose.yml: dind limits 1.5 CPU / 3 GiB → 1.0 CPU / 2.5 GiB — leaves headroom so Forgejo can always answer the runner. Trade-off: builds are somewhat slower and may occasionally hit the memory cap inside dind.

AppliedForgejo memory backstop

forgejo/compose.yml: 2 GiB memory cap on the forgejo container — the daily 05:00 restart resets the leak; this prevents a bad day from eating the box.

AppliedHost monitoring + Grafana alerts

observability/: added node-exporter (+ scrape job) and two alert rules — Host CPU > 90% and Host memory > 85%, both for 5 min. The CPU alert would have fired ~17:11 during the incident. Note: Grafana needs a contact point configured (UI) to push notifications.

Appliedbeszel alerts

Created via beszel API: CPU > 90%, Memory > 85%, Disk > 85%, each averaged over 5 minutes. Email (admin@trieoh.com) is configured; optionally wire ntfy push in the beszel UI for phone notifications.

AppliedAdd swap (4 GiB)

4 GiB swapfile active at /swapfile (persisted in /etc/fstab, priority -2). Removes the no-swap cliff — the box now has a memory buffer under load. Script kept in the repo: infra/scripts/add-swap.sh.

FutureMove Actions to a separate host

A 2-core box running prod + CI co-tenancy will keep hitting this wall. Dedicate a host (or bigger VM) to the runner.

InvestigatedForgejo "leak" — root cause found

Replicated Forgejo 10.0.3 locally (identical image, heavy churn for 1h): anon memory, Go heap and goroutines all flat — no Go heap leak. Prod decomposition: the 430MB cgroup is ~220MB of reclaimable page cache (no memory pressure → kernel never evicts); app anon is flat at ~191MB. The daily creep (264→466MB pre-fix) stopped after the runner interval fix — the old 2s-fetch / 1s-report polling was the driver. Keep the daily restart as belt-and-suspenders; monitor beszel for a few days to confirm.
