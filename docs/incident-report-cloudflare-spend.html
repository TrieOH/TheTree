Incident Report

Cloudflare Containers billed past the Workers Paid plan with no users

Window: 2026-10-19 → 2026-11-02 (detected 2026-11-02 11:27 UTC, mitigated 11:40, resolved 17:50)  ·  Severity: medium (financial, ~$23 over the plan; no outage, no data loss)  ·  Status: Resolved — spend now hard-capped inside the plan

Summary

A Cloudflare usage alert reported ~$20 of metered usage on an account with no users, on top of the $5 Workers Paid plan. The four backends (identityx, payssage, univents, informd) moved to Cloudflare Containers on Oct 19–23. Each ran up to 3 instances of the basic size (1 GiB / 4 GB) behind its Worker. Cloudflare bills a container's provisioned memory and disk for every second it is awake, and bills the Durable Object that hosts it for the same seconds. The APIs actually use 40–55 MB. Crons, cold-start JWKS fetches, a boot-time service chain and internet scanners kept the containers awake around the clock: 981 Durable Object hours in 9 days. The first fix (one lite instance, a 2-minute sleep, fewer wakers, a spend guard) went live at 12:12. A library quirk then kept IdentityX awake for another three hours; a second fix at 17:50 closed it.

Why it happened — in one sentence:

We paid for 1 GiB × 3 instances × 4 apps of reserved memory to run apps that use ~40 MB, and something always woke them up before the 5-minute sleep could kick in, on a platform that has no spending cap and reports overage a day late.

Root cause — four layers

  1. Billing model vs. app size. Containers bill provisioned memory and disk per second awake, plus DO duration for the same seconds. basic reserved 1 GiB for apps using ~40 MB (25× over). getRandom(env.X, 3) spread traffic over three instances, so a trickle of requests woke all three, each staying up for its 5-minute sleepAfter.
  2. Something always woke them.
    • Payssage cron every 15 min (96 wakes/day) and IdentityX hourly cleanups (24/day). Each wake costs ≥ 5 min awake.
    • Every other API fetched IdentityX's /.well-known/jwks.json on cold start: ~430 requests in 3 days.
    • Univents' boot check GetWallet called Payssage, whose API-key auth called IdentityX /auth/introspect: one cold start became three (55 calls on each side).
    • Scanners probing /, /.env, *.php, gcp-key.json reached the containers through the Workers.
  3. No hard cap. Cloudflare has no spending limit for usage products. Budget alerts are email-only and fire the day after the threshold is crossed. DO overage is billed in whole 1M GB-s blocks, so the first GB-s over the line cost $12.50.
  4. In-flight request leak (found after the first fix). @cloudflare/containers 0.3.7 counts a request as in flight until its response body is fully read, and a container never sleeps while the count is above zero. On the slower lite cold start, the edge gave up on JWKS requests (10 × 504). Nobody read those responses, so IdentityX stayed awake from 15:00 to 17:50 with no real traffic. The spend guard also over-counted: the library reports some stops late, and the guard counted the sleeping gap as awake time (univents: 889 GiB-s counted vs ~169 real).

Action items

AppliedInstance cap (immediate)

Containers API: max_instances 3 → 1 on all four apps at 11:40, before any code change.

AppliedRight-size and sleep sooner — PR #68

api/*/cloudflare: instance_type basic → lite (1/16 vCPU, 256 MiB, 2 GB), INSTANCES = 1, sleepAfter 5m → 2m, GOMEMLIMIT=200MiB so Go collects before the 256 MiB ceiling. Trade-off: CPU-heavy work (password hashing) is slower on 1/16 vCPU.

AppliedRemove the wakers — PRs #68 and #69

IdentityX crons hourly → once a day (03:00, cleanups + key rotation); Payssage redrive 15 min → every 6 hours. Univents boot wallet check off on Cloudflare (PAYSSAGE_VERIFY_WALLET_ON_BOOT=false). Workers answer scanner paths with 404 without waking a container (isNoise()). JWKS served from the edge cache and from KV for 1 hour, dropped right after keys.rotate. Access tokens 15 min → 1 h (fewer refreshes; trade-off: a revoked token stays valid up to an hour). Univents front reads attendee profiles through the query cache.

AppliedHard spend cap — lib/ts/container-budget

BudgetedContainer counts every container's awake GiB-seconds into KV container-budget. At 90% of the plan's 25 GiB-hours in a billing cycle (starts on the 24th), the APIs answer 503 instead of starting a container, until the next cycle. This is the guarantee: spend cannot leave the $5 plan. Trade-off: the APIs go down for the rest of the cycle if the budget runs out.

AppliedIdle watchdog and accurate counting — PR #69

A container with no new request for 5 minutes is stopped, whatever the library's in-flight count says. Late stop reports are clamped to the last request plus that window, so sleeping time is never counted. Trade-off: Univents' WebSocket/SSE connections drop after 5 idle minutes and reconnect on the next use.

AppliedPre-commit hook fix

.husky/pre-commit line 56 redirected engine_targets into the file it writes, failing every commit with "input file is output file".

WatchReconcile the guard with Cloudflare

After a few days, compare KV container-budget with containersUsageAdaptiveGroups. Expect idle days near zero and ~1–1.3 container-hours per hour of active use; the plan holds ~90 lite hours a month (~4.5 h per weekday).

FutureFaster cold starts on lite

IdentityX boot runs keys.EnsureAll with sequential Neon round trips per project before accepting traffic. Slow boots caused the 504s behind root cause 4; trimming boot work lowers both latency and awake time.

FutureMake the budget visible

Expose spent/limit from KV (a small endpoint or a Grafana panel) and warn at 50% and 75%, so a cut-off on the 20th isn't a surprise. Lower the Cloudflare budget alert to $1 in the dashboard as a second signal.

FutureRevisit the platform if usage grows

Containers bill reserved memory, and lite (256 MiB) is the smallest size. If real traffic outgrows ~90 hours a month, a fixed-price host runs all four APIs at ~40 MB each for less.

Day-1 follow-up (2026-11-03)

First 23 hours after the fix (Nov 2 18:00 → Nov 3 17:00 UTC). The fix holds: the four containers were awake 5.8 DO-hours in total, against ~98 h/day before (−94%). Container memory dropped from ~338k to ~3.1k GiB-s/day (−99%), under 1¢ a day at overage rates. No new DO block is coming: the 1M GB-s block bought on Nov 1 covers up to 1.4M, and the day used ~2.7k.

What still woke IdentityX

  • The JWKS KV copy never held. KV had no jwks: key a day later. The 1-hour TTL lapsed between wakes, and on a lite cold start the caller gave up (499/504) before the fill, so nothing was written.
  • So every cold start chained into IdentityX. Payssage's redrive cron at 00:00 and 06:00 woke Payssage, its JWKS fetch woke IdentityX. Each of those wakes lasted 4–6 min, because the abandoned JWKS request left the container to the 5-minute watchdog instead of the 2-minute sleep.
  • Scanners are mostly handled. Hundreds of .env/.php probes were answered 404 by the Workers. A few extensionless ones (/info, /api/status) still reach a container; rare enough to leave.

PR #70JWKS kept until keys can change

The KV copy lives 7 days and is dropped only when keys can change: container start (boot EnsureAll), keys.rotate, and project creation. The fill runs in waitUntil, so it lands even when the caller times out. Other APIs' cold starts stop waking IdentityX.

PR #70Skip the Payssage redrive on idle days

The Worker records the last write request or job it passed to Payssage. The 6-hourly webhook.redrive runs only when something happened since the previous run (15-minute margin over the sweep's 2-minute redriveAfter). Idle days: 4 cron wakes, each chaining into IdentityX, become 0.
