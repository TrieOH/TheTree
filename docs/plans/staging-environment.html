TrieOH · Deploy Plan

Staging Environment

A prod-twin staging stack on the same VPS — same images, same behavior, fresh data — so e2e tests run against a live server that behaves like prod, without touching prod.

Prod stays exactly as it is. A second, isolated stack runs alongside it under staging.* URLs: the same four services, the same pinned image tags, the same env shape. Its data is fresh — created by a bootstrap script, never copied from prod. E2e tests point at staging and get prod-like behavior on a live box. No dev environment.

└── thetree/
    ├── prod/                            # ← today's thetree/ moves here, name: thetree preserved
    │   ├── compose.yml                  #    (project name unchanged → volumes/networks untouched)
    │   ├── .env                         #    gitignored, server-only
    │   └── .identityx.env / .univents.env / .payssage.env / .informd.env
    └── staging/                         # ← new twin stack
        ├── compose.yml                  #    project thetree-staging, containers *-staging

        ├── bootstrap.sh [--reset]       #    one-time setup + reset

Why the prod move is safe: the compose name: thetree is what pins thetree_postgres_data / thetree_rustfs_* and the thetree_internal network. As long as name: doesn't change, moving the file to a subfolder changes nothing on disk — only the deploy command becomes cd ~/deploy/thetree/prod && docker compose up -d (ADR-0007's "server" section gets updated).

Container names get suffixes (postgres-staging, identityx-staging …) — two containers can't both be named postgres on one host. That's a Docker constraint, not repo style.

Step by stepHow it works

  1. The deploy repo gains thetree/prod/ (moved, name: thetree untouched) and thetree/staging/ (compose + env templates + bootstrap.sh).
  2. Caddy (infra repo) gets staging.api.* / staging.auth.* blocks proxying to *-staging:8080; just reload-caddy.
  3. 8 DNS records point the staging API subdomains at the VPS origin (plain A, grey-cloud so Let's Encrypt works). Frontend subdomains need no DNS — they're Cloudflare worker custom domains.
  4. On the server: fill staging envs from the prod templates with fresh secrets, docker compose up -d, run ./bootstrap.sh once.
  5. Staging frontends deploy as 4 new workers (wrangler --env staging), each bound to its staging.* subdomain.
  6. E2e tests hit staging.* URLs; test emails are read through the SSH tunnel; payments run in test mode.

The stackStaging compose

Mirror of prod's compose.yml with four deltas:

  • Project/containers: name: thetree-staging, containers postgres-staging, rustfs-staging, identityx-staging, univents-staging, payssage-staging, informd-staging — own volumes and network.
  • mailpit instead of real SMTP — every service's SMTP_HOST points at it.
  • No obs-net — staging must not pollute prod observability. (Amended 2026-08-24 — see flag below.)
  • Loopback debug ports (127.0.0.1:18080 → identityx, 127.0.0.1:18082 → payssage) so server-side scripts and smoke tests can call the APIs directly.
Amendment (2026-08-24): the "no obs-net" delta is revised — staging should ship telemetry, into the same Victoria instances with an env="staging" stream label (a second Victoria stack doesn't fit 8GB RAM), with all prod alerts filtered to env="prod". Blind staging is undebuggable staging — without telemetry, the e2e errors this plan exists to catch are invisible. See docs/infra-wishlist.md #18.

Same pinned image tags as prod (identityx:v0.35.3, univents:v0.10.4, payssage:v0.7.4, informd:latest), bumped alongside prod so staging always previews the current prod behavior.

Bootstrap & reset

./bootstrap.sh          # first run:  up → identityx /auth/setup → projects →
                        #             svc actors + API keys → payssage wallet
                        #             (sandbox + fee + webhook → univents-staging)
./bootstrap.sh          # re-run:     idempotent — detects what exists, fills gaps
./bootstrap.sh --reset  # teardown:   docker compose down -v (wipes postgres/rustfs)
                        #             → up → full fresh bootstrap
docker compose down     # stop without wiping

Written into each service's env file (.<svc>.env, gitignored, server-only): IDENTITY_X_PROJECT_ID / IDENTITY_X_API_KEY per service, plus PAYSSAGE_WALLET_ID / PAYSSAGE_WEBHOOK_SECRET / PAYSSAGE_API_KEY for univents.

Email — readable via SSH tunnel

mailpit binds to loopback only (127.0.0.1:8026), so it's reachable from your machine but not the internet:

ssh -N -L 8026:127.0.0.1:8026 trieoh@<server>   # then open http://localhost:8026
  • UI: read every email staging sends (verify links, badge QRs, whatever e2e triggers).
  • API (http://127.0.0.1:8026/api/v1/messages): e2e tests running on the server can assert "an email with subject X was sent".
  • SMTP (1025) stays internal-only — staging services deliver there, nothing reaches real inboxes.

The Cloudflare partFrontends: prod & staging on different subdomains

A worker's VITE_* config is baked in at build time — staging must point at staging.api.* URLs, prod at api.*. One worker can't serve both, so each app gets two separate workers, each bound to its own subdomain:

AppProd workerStaging workerStaging subdomain
identityxidentityxidentityx-stagingstaging.identityx.com.br
univentsuniventsunivents-stagingstaging.univents.com.br
payssagepayssagepayssage-stagingstaging.payssage.trieoh.com
informdinformdinformd-stagingstaging.informd.trieoh.com

Mechanism: wrangler environments

Wrangler's env feature deploys a separate worker named <name>-<env> with env-scoped routes. One config file, no duplication. In front/univents/wrangler.jsonc (same shape for all four):

{
  "name": "univents",
  "main": "src/server.ts",
  // ... existing fields untouched ...
  "env": {
    "staging": {
      "routes": [
        { "pattern": "staging.univents.com.br", "custom_domain": true }
      ]
    }
  }
}

Deploy with:

pnpm -F univents build          # VITE_API_URL=https://staging.api.univents.com.br/ baked in
wrangler deploy --env staging   # creates/updates worker "univents-staging" + attaches the route

Prod keeps deploying exactly as today (wrangler deploy, no --env) → worker univents. Its routes are dashboard-managed and untouched.

Routing: no DNS needed for frontends

custom_domain: true tells Cloudflare this is a Worker Custom Domain — CF auto-provisions the routing internally, no record needed, as long as the zone is in the account (all three zones are: they're proxied today).

browser → staging.univents.com.br ──CF──▶ worker "univents-staging" ──▶ staging.api.univents.com.br
                                                                           (A record → VPS)
                                                                                │
                                                                           Caddy → univents-staging:8080

The only DNS you add is the 8 staging.api.* / staging.auth.* A records for Caddy.

Secrets & workflow

AUTH_SESSION_PASSWORD is a runtime secret, per worker, set once (fresh value per env):

wrangler secret put AUTH_SESSION_PASSWORD --env staging   # applies to univents-staging

A small Forgejo workflow (.forgejo/workflows/deploy-front-staging.yml, same paths filter as prod's) builds each front with staging vars and runs wrangler deploy --env staging:

jobs:
  deploy-staging:
    strategy:
      matrix:
        include:
          - app: identityx
            api_url: https://staging.api.identityx.com.br/
          - app: univents
            api_url: https://staging.api.univents.com.br/
            auth_url: https://staging.auth.univents.com.br/
          - app: payssage
            api_url: https://staging.api.payssage.trieoh.com/
            auth_url: https://staging.auth.payssage.trieoh.com/
          - app: informd
            api_url: https://staging.api.informd.trieoh.com/
            auth_url: https://staging.auth.informd.trieoh.com/
    steps:
      - run: pnpm -F ${{ matrix.app }} build
        env:
          VITE_API_URL: ${{ matrix.api_url }}
          VITE_AUTH_API_URL: ${{ matrix.auth_url }}
      - uses: cloudflare/wrangler-action
        with:
          command: deploy --env staging
          workingDirectory: front/${{ matrix.app }}

Why VITE_AUTH_API_URL is set explicitly: prod's identityx/univents builds never pass it, so staging does — that's also why the Caddyfile gets the staging.auth.* aliases (→ identityx-staging). The identityx staging build keeps prod's behavior (no auth_url in its matrix row).

Why not a copyStaging is a twin, not a prod-data copy

An earlier version of this plan had staging restored from prod dumps. Data flows one way (prod → staging), but a copy drags prod's trust into staging, and every one of these leaks is staging acting on prod's reality:

  • Email — staging holds prod's users; with real SMTP, verify/badge mail lands in real inboxes pointing at staging.* URLs.
  • Money — copied payssage data includes sellers wired to real MercadoPago accounts; a checkout could charge them.
  • Webhooks — the copied wallet's webhook endpoint points at prod's univents URL; a copied secret means prod accepts staging events and mutates prod state.
  • Token trust — identityx signing keys live in the DB; a copy lets staging mint JWTs prod verifies as valid.
  • PII — real users' data in a lower environment, needing a sanitize pass on every refresh.

Keeping staging fresh-data removes all five: no sanitize pass, no refresh script, no key rotation, no webhook re-pointing. E2e tests create their own actors and events on staging.

Do it in orderApply checklist

  1. deploy repo: git mv thetree thetree/prod… (or git mv thetree/compose.yml thetree/prod/ + envs), commit. Add thetree/staging/ files, commit.
  2. infra repo: add the 8 Caddyfile blocks, commit, push, just reload-caddy on the server.
  3. DNS: create the 8 records (grey-cloud). Wait for propagation.
  4. TheTree repo: wrangler env sections ×4 + staging workflow, commit, push.
  5. Server: cd ~/deploy && git pull; cp thetree/prod/.env thetree/staging/.env etc., then change all secrets (DB/object-storage passwords, ENCRYPTION_KEY, HMAC_SECRET, WS_JWT_SECRET, SMTP→mailpit, TEST_MODE=true).
  6. cd thetree/staging && docker compose up -d && ./bootstrap.sh
  7. Smoke test: curl https://staging.api.identityx.com.br/health, log in via a staging front, check mailpit through the tunnel.
  8. Deploy staging workers (workflow or wrangler deploy --env staging ×4), wrangler secret put AUTH_SESSION_PASSWORD --env staging ×4.
