1 · Executive summary

Refunds are already half-wired: payssage normalizes MP's refunded status into its intent model and already delivers payment.refunded D2-envelope webhooks to univents; univents' receiver has the eventRefunded case stubbed out per design decision D1 (deferred). What's missing is the refund action (payssage has no Refund op), the refund reaction (no refunded purchase status or state flip), and the organizer initiation surface (no edition-purchase read, no refund endpoint, no admin UI).

This version of the plan is scoped down hard by a design-review pass (12 decisions, §2) and verified against the code (§13 inspection log — several planned items turned out to already exist, e.g. badge revocation and the identityx actor lookup). Net effect: the build is ~6 slices (the first is fee observability + external_id/external_group intent tagging, §5/A7); the payssage frontend, partial refunds, a "refunding" state, WS frames, and eligibility rules are all cut.

Free lunch found during inspection: badge revocation on refund is one call to the existing RevokeByRegistration op; the buyer identity for the admin list can come from a new payer_email column (the front already sends the payer's email at checkout) plus the existing attendee_name/email on registrations — no IdentityX resolution machinery needed.
Fee observability (§5) — verified working: the wallet fee is set in prod and the cut is being charged and received (verified: 2,25 on a 45,00 payment lands in the marketplace account as "Venda Principal") — the earlier confusion was checking the wrong account and MP's settlement hold (a liberar until the release date). Slice 1 captures MP's fee + release fields (fee_details, net_received_amount, money_release_date/status) into the intent so balance/commission questions are answerable in-app, and fee-on-refund behavior (R1) becomes verifiable before sign-off.

3 · How payment works today

1Checkout api/univents/internal/services/checkouts/checkout.go — Tx1 reserves items (FOR UPDATE locks, server prices, availability), materializes the purchase (pending) + purchase_items + registrations/product_purchases/participations, schedules the 10:01 expiry job, issues the WS token. Post-commit creates the payssage intent; Tx2 attaches payssage_intent_id (+ pix QR). Free orders confirm immediately. Checkout never self-approves (D3).
2Payssage checkout api/payssage/internal/features/providers/mercado_pago_provider/checkout.go — POST https://api.mercadopago.com/v1/payments with the seller's MP token, transaction_amount, application_fee (from wallet fee_bps), external_reference = intent UUID, payer CPF/email, pix or card. Stores the MP payment id in provider_data.
3MP webhook → payssage internal/services/webhooks/receive.go — verify signature, re-fetch GET /v1/payments/{id}, normalize status, persist webhook_events (deduped on provider+external_id+event_type), dispatch D2 deliveries (HMAC-signed, retried ≤5×).
4D2 envelope → univents internal/handlers/webhooks/receive_payssage_webhook.go → services/webhooks/receive.go — HMAC verify, correlate intent→purchase (D3 card-race re-query), switch on event_type.
5Approve services/webhooks/approve.go — guarded pending→approved, cancel expiry job, flip rows (registration confirmed + badge emit, product_purchase confirmed), NOTIFY univents_changes → WS purchase.confirmed + SSE stock delta.

Failure paths: payment.failed|rejected|cancelled → cancel() flips pending→… and rows to cancelled. Expiry frees the reservation; a late approval either honors the order or marks status_reason = refunded_after_expiry (D1 manual reconciliation — stays manual, D-10).

4 · Mercado Pago refund facts

Endpoint: POST https://api.mercadopago.com/v1/payments/{payment_id}/refunds — "Create Partial/Full Refund for a specific payment."
FactDetail
Full vs partialOmit amount → full refund. Include amount → partial (errors 4040/4041 for bad amounts). v1 uses full only.
AuthAuthorization: Bearer {seller_access_token} — the same per-seller token payssage already stores from the MP OAuth callback.
IdempotencyX-Idempotency-Key expected (4292 Header-X-Idempotency-Key-can't-be-null); needed so a retry never double-refunds.
Refund statusesRefund object: approved, rejected, pending, canceled, authorized. Refund is async from the buyer's side.
Payment statusFull → refunded; partial → partially_refunded. Payment carries a refunds[] array.
Time window2024/15016 Payment too old to be refunded — refunds are time-limited (~180 days for BR, verify).
Cancel ≠ refundCancellation (what CancelPendingPayment does) is for not-yet-approved payments; refunds reverse approved ones.
BalanceRefunds come from the seller's MP balance — insufficient funds → refund rejected (accepted limitation, D-12).
WebhooksNo dedicated refund topic — status changes ride the payment topic; payssage already re-syncs and normalizes refunded → payment.refunded in the D2 envelope.
Feepayssage charges application_fee (verified working, §5). Fee-on-refund is NOT documented by MP — searched official docs PT/EN/ES, API refs, blog, community, third-party guides: the split mechanics are documented, the refund behavior of the commission is not. Answer empirically (see R1).

5 · Fee mechanics & observability (verified working in prod)

5.1 How the fee works

The code path is sound and short — verified end-to-end in prod:

  1. Wallet fee configured via PATCH /wallets/{id}/fee (fee_bps; UI exists — front/payssage/src/features/wallets/ui/wallet-card.tsx "Edit fee", displayed as a %). Prod wallet: fee_bps = 500.
  2. At checkout, payssage reads wallet.FeeBps (api/payssage/internal/features/providers/mercado_pago_provider/checkout.go L43–49): feeBps := wallet.FeeBps; if feeBps == 0 { feeBps = checkoutData.MarketplaceFeeBPS }. Univents never sends marketplace_fee_bps, so feeBps = wallet fee.
  3. application_fee = calcApplicationFee(amountCents, feeBps) is sent on the MP payment; MP deducts it from the seller and credits the marketplace account (owner of the payssage application).

5.2 Status: verified — the cut is charged and received

Prod-verified. Payment 174515095132 (R$ 45,00): MP applies application_fee = 2.25 (5% = fee_bps 500), the seller nets 42.30, and the marketplace account shows the credit as "Venda Principal — R$ 2,25". No bug; the earlier confusion was checking the wrong account and MP's settlement hold: 
{"status": "approved", "transaction_amount": 45,
 "fee_details": [
   {"amount": 0.45, "fee_payer": "collector", "type": "mercadopago_fee"},
   {"amount": 2.25, "fee_payer": "collector", "type": "application_fee"}
 ],
 "net_received_amount": 42.3}
// 2.25 = 5% of 45.00; net = 45 − 2.25 − 0.45 ✓
Settlement note: the credit appears in the account immediately but sits a liberar until MP's release date (pix D+1+, cards on capture) — the available balance moves only on release. If a release date passes with no movement, that's an MP account-hold (verification/KYC), not an integration issue.

5.3 Slice 1 — capture MP fee + release fields (in scope now)

Make fee and settlement state observable at the source, in api/payssage:

  • Model (models/mercado_pago.go): extend MercadoPagoIntentData with FeeDetails (raw array: type incl. application_fee/mercadopago_fee, amount, fee_payer), NetReceivedAmountCents, TotalPaidAmountCents, the echoed ApplicationFeeCents, and MoneyReleaseDate + MoneyReleaseStatus (MP's settlement fields — the answer to "where's my money" without the panel). Exact response field names to confirm against one live payment before finalizing.
  • Provider (features/providers/mercado_pago_provider/checkout.go): extend the MP response struct to read those fields and marshal them into provider_data on every checkout.
  • Exposure: provider_data already returns on GET /intents/{id} and the wallet intents list — no API change. (Dashboard display is optional ops convenience, out of the cut scope unless wanted.)
  • Tests: checkout_test.go asserts the captured fields against a canned MP response.
  • Future use: the same captured data answers R1 (fee-on-refund) — refund a fee'd payment and read what MP returns for the fee portion.

A7 · external_id + external_group on intents (purchase + edition)

Resolves the TODO at checkout.go L94 ("remember to use external group feature we made") — there is no built feature yet; this adds it. Every payment intent gets two first-class, queryable fields set by univents at checkout:

  • external_id = purchase id (the caller's order)
  • external_group = edition id (groups all payments of an edition)

Naming invariant (document in the spec): every external_* field holds the id of the counterparty, never our own — MP payment external_reference = payssage intent id; intent external_id/external_group = univents purchase/edition ids. The webhook event's external_id is a different object and meaning (the provider's MP payment id, used for the dedupe index) — keep the two documented separately.

  • payssage model (models/intents.go): add ExternalID *string + ExternalGroup *string to Intent, CreateIntentInput and HardCreateIntentInput (testmode).
  • DB: migration 006_external_group.sql (next after 005_webhooks): ALTER TABLE intents ADD COLUMN external_id TEXT; + ADD COLUMN external_group TEXT; + CREATE INDEX idx_intents_external_group ON intents (external_group); — no backfill inside the migration (only one edition in prod; existing intents get marked by hand afterwards).
  • Manual backfill (one-time prod ops step, after deploy) — univents already stores both ids on every checkout intent as metadata->>'purchase_id' / metadata->>'edition_id', so a single hand-run UPDATE marks all current intents:
-- run by hand in prod once (not part of the migration)
UPDATE intents SET
    external_id   = metadata->>'purchase_id',
    external_group = metadata->>'edition_id'
WHERE metadata->>'purchase_id' IS NOT NULL;

-- verify: any succeeded intent left NULL never carried the metadata
-- (testmode hard-creates, non-univents callers) — expected to be a small set;
-- single-edition prod means this should mark everything real
SELECT count(*) AS null_id FROM intents WHERE external_id IS NULL;
SELECT count(*) AS null_group FROM intents WHERE external_group IS NULL;
  • Verification (post-backfill): spot-check one succeeded intent per edition via SELECT external_id, external_group, metadata FROM intents WHERE status = 'succeeded' LIMIT 5; — both should match their metadata counterparts.
  • Service (services/intents/checkout.go): set ExternalID: payload.ExternalID + ExternalGroup: payload.ExternalGroup on the intent before provider.Checkout; testmode hard_create accepts both.
  • Spec + handler: CreateIntentRequest.external_id + external_group (optional strings) and Intent.external_id + external_group in api/payssage/api-spec.yml; handler passes them through. Exposed on get/list (no filter endpoint in v1 — the group index is there when filtering is wanted).
  • univents (api/univents/internal/services/checkouts/checkout.go buildIntentRequest): send ExternalID = purchase.ID.String() + ExternalGroup = editionID.String() (both already in scope; currently ride in metadata — promoted to queryable fields, metadata kept for backward compat).
  • SDKs: Go (sdk/go/Payssage/intents.go/types.go) add both fields to CreateIntentRequest + Intent; regen the TS SDK. Tests: create intent with both, assert they round-trip on get/list.
